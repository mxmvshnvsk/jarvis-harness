# ADR-0010: Фильтрация секретов на всех границах, включая экспорт telemetry

- Статус: принято
- Дата: 2026-10-03
- Основание: [ADR-0001](0001-target-architecture.md) §13 («sensitive paths и секреты фильтруются до
  попадания в model context/artifacts», «credentials и MCP auth никогда не передаются модели»), §14
  (экспортируемый telemetry backend), §17 (Telemetry: экспортируемый backend adapter);
  [ADR-0009](0009-ci-mode-and-human-gate.md) §5 (бандлы покидают машину)
- Код (план): `src/security/redactor.ts` (единый компонент), `src/security/detectors/{paths,patterns,env}.ts`,
  применение в `src/tools/router.ts`, `src/artifacts/store.ts`, `src/telemetry/{events,export}.ts`,
  `src/orchestration/bundle.ts`, `src/cli/output.ts`; тесты `tests/security/leaks.test.ts`

## Контекст

ADR-0001 ставит фильтр перед model context и artifacts. Но у Jarvis есть ещё каналы, по которым данные
покидают машину разработчика: экспорт traces в корпоративный backend (stdout/stderr tool calls, аргументы
MCP, фрагменты файлов), бандлы export/import, вывод CLI в логи CI. Любой из них без фильтра — утечка
`.env`, токенов из конфигов legacy-проекта, PEM-ключей из fixtures. Фильтр нужен один, применяемый на всех
границах, а не три разных в трёх местах.

## Решение

### 1. Один Redactor, применяемый на границах

| Граница | Когда | Режим |
| --- | --- | --- |
| tool result → контекст модели | при сборке ContextPackage | read-time |
| что угодно → artifact store | при записи blob | write-time |
| что угодно → telemetry events / экспорт | при записи события | write-time |
| что угодно → export-бандл | при сборке | write-time (повторно, на случай старых записей) |
| CLI stdout/stderr, логи | при выводе | write-time |

Принцип: Jarvis **не хранит** сырые секреты ни в одном durable-хранилище, даже локальном. Это
осознанная потеря по отношению к «sources survive summaries» (ADR-0001 §7): секрет — не evidence. Чтобы
не терять связи, замена детерминирована: `[REDACTED:<type>:<hash8>]`, где `hash8` — первые 8 hex
`sha256(salt_run, value)`. Одно и то же значение в одном Run даёт один placeholder (корреляция сохраняется,
значение — нет); между Run — разные (нельзя сопоставить).

### 2. Детекторы, по убыванию точности

1. **Точные значения из окружения.** Любая переменная процесса, чьё имя соответствует
   `*TOKEN*|*SECRET*|*PASSWORD*|*PASSWD*|*API_KEY*|*PRIVATE*|*CREDENTIAL*` (плюс список в
   `project.yaml: security.secretEnv`), и значения, полученные Tool Router'ом из keychain, добавляются в
   литеральный набор; любое вхождение значения (длиной ≥ 8) в любом тексте редактируется. Это ловит
   корпоративные токены независимо от формата.
2. **Запрещённые пути** — `.env*`, `**/secrets/**`, `**/*.pem`, `**/*.key`, `~/.ssh`, `~/.aws`, `~/.npmrc`,
   `~/.jarvis/config.yaml` (секции credentials), список расширяется в `project.yaml`. Чтение таких путей
   **отвергается** Tool Router'ом до вызова инструмента (policy denial, событие `security.pathDenied`), а
   не редактируется постфактум. Директории с секретами также исключены из Project Graph (ADR-0008) и
   retrieval.
3. **Шаблоны** — известные префиксы (`AKIA…`, `ghp_`, `gho_`, `xox[abp]-`, `sk-`, `AIza…`), JWT, PEM-блоки,
   `Authorization: Bearer …`, basic-auth в URL, пары `password|secret|token\s*[:=]\s*\S+`, строки высокой
   энтропии длиной ≥ 32 в контексте присваивания. Корпоративные форматы — `project.yaml:
   security.secretPatterns` (регулярные выражения с именем типа).

### 3. Telemetry export — отдельно строже

Экспортер в корпоративный backend работает по **allowlist полей** схемы событий: метрики, идентификаторы
(run/step/agent/actor), имена capability, коды ошибок, длительности, счётчики токенов, ссылки на артефакты.
Содержимое — stdout/stderr инструментов, аргументы, фрагменты файлов, тексты промптов — не экспортируется,
если не включено явно `telemetry.export.payloads: true`; при включении — только после Redactor'а и с
ограничением размера (`telemetry.export.maxPayloadBytes`, по умолчанию 4 KiB на поле, остальное —
усечение с пометкой). Полные данные остаются в локальном artifact store с retention. Это безопасный
дефолт: backend видит, *что* происходило, а не *что именно* читали.

### 4. Наблюдаемость самого фильтра

Каждая замена — событие `security.redaction { type, boundary, count }` без значения. `jarvis doctor`
показывает статистику за период; всплеск `pattern:high-entropy` в research-фазе — повод посмотреть на
проект, а не на Jarvis. `jarvis context` помечает отредактированные места в предпросмотре контекста.

### 5. Тестирование

`tests/security/leaks.test.ts`: корпус синтетических секретов всех типов прогоняется через каждый
сериализатор-границу (контекст, artifact blob, telemetry event, бандл, CLI-вывод); тест падает при любом
вхождении исходного значения. Корпус — часть репозитория; добавление нового типа секрета начинается с
добавления его в корпус. Корпоративные шаблоны тестируются тем же механизмом из `project.yaml` при
`jarvis doctor --security`.

### 6. Известные ограничения

Шаблоны и энтропия — эвристика; секрет нестандартного формата, не присутствующий в окружении, может пройти.
Поэтому порядок детекторов именно такой: точные значения и запрет путей закрывают основные случаи, шаблоны —
остаточный риск; экспорт payload'ов выключен по умолчанию, чтобы остаточный риск оставался на машине
разработчика.

## Последствия

- Один компонент, одна таблица детекторов, один тест — вместо трёх несогласованных фильтров.
- Корпоративный backend по умолчанию получает только метаданные; включение payload'ов — явное решение
  безопасности, а не дефолт.
- Детерминированный placeholder сохраняет пригодность traces для анализа («тот же токен в трёх местах»).
- Запрет путей делает некоторые legacy-конфиги невидимыми для агентов; это правильно, но `doctor` должен
  объяснять, почему файл «не найден».

## Альтернативы

- **Фильтр только перед моделью.** Закрывает утечку в LLM-провайдера, но не в telemetry-backend и бандлы —
  куда данные тоже уходят с машины.
- **Хранить сырые данные локально, редактировать при экспорте.** Удобно для отладки, но локальный
  `jarvis.db` и artifact store копируются, бэкапятся и попадают в бандлы; один write-time фильтр надёжнее.
- **Редактировать всё с высокой энтропией без типизации.** Ломает хэши, sha коммитов, UUID — ровно те
  идентификаторы, на которых держится provenance.
