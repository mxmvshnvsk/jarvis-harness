# ADR-0012: Evals — ярусы кейсов, скоринг и record/replay модельных вызовов

- Статус: принято
- Дата: 2026-10-03
- Основание: [ADR-0001](0001-target-architecture.md) принцип «Measure first», §14 (evals сравнивают
  thresholds, routing, topology, retrieval), §17 (Vitest + fixture-репозитории), §21 («новые агенты, RAG и
  orchestration complexity принимаются только после измеримого улучшения evals»);
  [ADR-0005](0005-artifact-versions-provenance.md) §6 (diff человека сохраняется всегда),
  [ADR-0009](0009-ci-mode-and-human-gate.md) §5 (бандл как формат переноса)
- Код (план): `src/evals/{cases,scorers,runner,report}.ts`, `src/models/gateway/cassette.ts`,
  `tests/fixtures/repos/*`, `evals/cases/*.yaml`, `evals/results/`, CLI `jarvis evals run|baseline|diff`,
  `jarvis run-to-case <run>`

## Контекст

ADR-0001 требует измерять, но не определяет, что такое eval-кейс, откуда берутся кейсы и как
тестировать workflow-логику без живой модели. Живая модель за корпоративной квотой 60k output / 20 мин —
дорогой и недетерминированный ресурс; тесты на ней либо не запускаются, либо флакают. Без определённого
скоринга «улучшение evals» — мнение.

## Решение

### 1. Три яруса кейсов

| Ярус | Что проверяет | Откуда кейсы | Модель |
| --- | --- | --- | --- |
| Компонентный | Context Builder, compaction, retrieval, Project Graph, Policy Engine | рукописные фикстуры; «fact cards»: после compaction в контексте обязаны остаться факты X, Y, Z; retrieval обязан вернуть источники S | без модели или replay |
| Workflow | SDD-workflow целиком на fixture-репозитории | синтетические задачи с известным ответом: файлы, которые должны быть затронуты; тесты, которые должны пройти; acceptance criteria, которые должны попасть в spec | replay в CI, live по расписанию |
| Production-derived | качество на реальных задачах | завершённые Run (§3) | live по расписанию, с бюджетом |

### 2. Скоринг — детерминированный первым

Скореры в порядке приоритета: прошли ли тесты; recall затронутых файлов против gold; recall обязательных
источников (required evidence); покрытие acceptance criteria; число итераций по обратным рёбрам
(ADR-0004); расход output-токенов. LLM-as-judge допускается только для качества review-находок и
читаемости spec, с закреплённой моделью и версией промпта судьи в результате; изменение судьи = новая
baseline.

Метрика верхнего уровня — **task success на 10k output-токенов**. Без нормировки на стоимость «ещё один
агент» выигрывает всегда.

### 3. Завершённый Run → кейс

`jarvis run-to-case <run>` собирает из бандла (ADR-0009 §5) кейс: задача и её входные источники, gold —
финальный diff, принятый человеком (`jarvis apply`), размеченные коррекции — human-версии артефактов и их
diff против агентских (ADR-0005), required evidence — источники, на которые ссылаются human-версии spec и
impact. Секреты уже отредактированы (ADR-0010); кейс проходит ручную проверку перед включением в набор,
потому что содержит корпоративный контекст — набор production-derived живёт во внутреннем репозитории
проекта, не в Jarvis.

### 4. Record/replay в ModelGateway

`ModelGateway.mode: live | record | replay`. Кассета — запись `{ key, request, response, usage, model,
timestamp }`, где `key = sha256(modelId, нормализованный ContextPackage, params, schema)`. В `record`
вызовы идут в модель и пишутся; в `replay` — ищутся по ключу, промах — ошибка теста (не тихий live).
Кассеты — файлы в `tests/cassettes/` (компонентный и workflow ярусы) и в бандле Run (production-derived).

Что это даёт: unit/integration-тесты runtime, policy, обратных рёбер и resume без квоты и без флаков;
регресс на изменение промпта виден как промах кассеты, а не как случайный провал.

Ограничение: кассета инвалидируется при любом изменении контекста; для тестов runtime это желаемое
поведение, для тестов промптов — кассета перезаписывается осознанно (`jarvis evals record`).

### 5. Эксперименты и baseline

`jarvis evals run --suite <s> --variant key=value…` прогоняет набор с вариантами конфигурации (пороги
compaction 50/60/70, модель роли, включённый semantic retrieval) и пишет `evals/results/<date>-<suite>.json`.
`jarvis evals baseline` закрепляет результат; `jarvis evals diff` сравнивает с baseline и возвращает
ненулевой код при регрессе сверх допуска (на метрику, из конфига). В CI Jarvis прогоняется компонентный
и workflow ярусы в `replay`; live-прогоны — по расписанию daemon'ом с отдельным `quotaPool: evals`.

### 6. Decision gate

Архитектурные добавления из ADR-0001 §21 (новый агент, embeddings, параллельные ветки) требуют
прогона §5 с вариантом «до/после» и улучшения метрики верхнего уровня или одной из метрик §2 без ухудшения
остальных сверх допуска. Результат прикладывается к ADR добавления.

## Последствия

- Workflow-логика тестируется в CI детерминированно; живая модель нужна только для evals качества.
- Каждый принятый Run бесплатно пополняет набор; человеческие правки становятся разметкой.
- Нужна дисциплина: кейсы production-derived проходят ревью и живут в закрытом контуре.
- Кассеты — крупные файлы; хранятся с ограничением размера и retention, не в git LFS (его нет в контуре),
  а как обычные файлы с усечением payload'ов по правилам ADR-0010 §3.

## Альтернативы

- **Только LLM-as-judge.** Дорого, недетерминированно, судья дрейфует вместе с моделью.
- **Моки модели вручную.** Не масштабируются и не отражают реальные ответы; кассеты — те же моки, но
  записанные.
- **Evals только live.** Невозможны в CI при текущей квоте; флаки обесценивают сигнал.
