# ADR-0013: Context pressure — знаменатель, пороги, подсчёт токенов и prefix cache

- Статус: принято
- Дата: 2026-10-03
- Основание: [ADR-0001](0001-target-architecture.md) §7 (слои L0–L5, таблица context pressure, «60% —
  стартовая гипотеза, порог настраивается по модели и подтверждается evals»), §10 (ModelGateway собирает
  usage); [ADR-0007](0007-model-capabilities.md) §1 (`contextWindow`, `maxOutput`, `tokenizer`,
  `supports.prefixCache`), [ADR-0012](0012-evals-and-record-replay.md) §5 (варианты порогов)
- Код (план): `src/context/pressure.ts` (расчёт), `src/context/tokens.ts` (оценка и калибровка),
  `src/context/serialize.ts` (байт-стабильная сериализация слоёв), профили порогов в конфиге
  (`context.thresholds`), метрики `context.*` в telemetry

## Контекст

Таблица порогов в ADR-0001 задана в процентах без знаменателя. У DeepSeek Flash и Qwen Coder разные
окна, разные лимиты output и разные токенизаторы, которых в закрытом контуре может не быть. Если
знаменатель — номинальное окно, то при `maxOutput` 8k и structured output шаг упрётся в лимит раньше, чем
сработает compaction. Отдельно: если корпоративный endpoint поддерживает prefix caching, порядок и
стабильность слоёв контекста напрямую влияют на расход квоты, а ADR-0001 этого не фиксирует.

## Решение

### 1. Знаменатель

```
effective = min(model.contextWindow, policy.maxContext)
          − reserveOutput(role)        // maxOutput модели или лимит роли из policy, что меньше
          − safety                     // 5 % от окна
pressure  = estimatedPromptTokens / effective
```

`policy.maxContext` позволяет искусственно ограничить окно дешёвой/быстрой работы (например, 64k у
128k-модели для review) — это конфиг проекта, не свойство модели.

### 2. Пороги — профиль на модель и фазу

```yaml
context:
  thresholds:
    default:        { watch: 0.40, compact: 0.60, aggressive: 0.75, reset: 0.85 }
    byModel:
      qwen-coder:   { compact: 0.55 }          # переопределяется только отличие
    byPhase:
      research:     { reset: 0.90 }            # reset всё равно на границе фазы
      implementation: { compact: 0.50 }        # diff и tool output растут быстро
```

Разрешение: `byPhase` поверх `byModel` поверх `default`. Значения — объект экспериментов ADR-0012 §5;
ADR не фиксирует «правильные» числа, он фиксирует, что они конфигурируемы по этим двум осям и измеряются.

### 3. Подсчёт токенов — самокалибровка

Оценка до вызова — по семейству токенизатора из дескриптора модели: если доступен локальный токенизатор
(tiktoken-совместимый, без сети), используется он; иначе — эвристика `chars / k` с `k` по семейству.
После каждого ответа Gateway сравнивает `usage.prompt_tokens` с оценкой и обновляет коэффициент
`k[modelId]` экспоненциальным сглаживанием (α = 0.2); хранится в `~/.jarvis/cache/models/<id>.calib.json`.
Через ~10 вызовов погрешность оценки — единицы процентов без установки чужих токенизаторов. Оценка всегда
берётся с запасом (`× 1.05`) — лучше compaction на шаг раньше, чем отказ endpoint'а.

### 4. Prefix cache

Слои L0 (system/security/policy), L1 (task/spec/constraints), L2 (current state/decisions) сериализуются
**байт-стабильно**: фиксированный порядок секций, отсортированные ключи, без временных меток и счётчиков в
тексте, без «обновлено N минут назад». Внутри шага L0–L2 не меняются между вызовами; L2 обновляется только
на границе шага/итерации. L3–L5 (working set, retrieved, tool history) идут строго после и растут только
в конец: trimming удаляет из хвоста L5, не переупорядочивая начало.

Для моделей с `supports.prefixCache` Gateway пишет `usage.prompt_cache_hit_tokens` (DeepSeek отдаёт его
явно; для других — отсутствие метрики) в событие `model.call`; метрика `context.cacheHitRatio` на шаг —
часть отчёта `jarvis stats`. Падение ratio после правки промптов — сигнал, что кто-то поместил переменную
часть в стабильный слой.

### 5. Что считается при pressure

В `estimatedPromptTokens` входит всё, что уйдёт в запрос, включая схему structured output и описания
инструментов, выданных агенту (их размер — отдельная метрика `context.toolSchemaTokens`: раздутый список
capability — частая скрытая причина pressure).

### 6. Действия по порогам

Остаются как в ADR-0001 §7: `watch` — trimming L5; `compact` — семантическая компакция L3–L5 до целевого
размера (`context.compactTarget`, по умолчанию 35 %); `aggressive` — компакция + ужесточение retrieval;
`reset` — structured handoff и новая сессия агента. Компакция никогда не трогает L0–L1 и не меняет байты
L2 внутри шага (иначе теряется prefix cache на ровном месте).

## Последствия

- Пороги сравнимы между моделями, потому что знаменатель учитывает output-резерв.
- Нет зависимости от внешних токенизаторов; точность достигается калибровкой по фактическому usage.
- Дисциплина сериализации слоёв становится проверяемой метрикой, а не пожеланием.
- Числа порогов — предмет evals; ADR не устареет при их изменении.

## Альтернативы

- **Проценты от номинального окна.** Срабатывает слишком поздно при большом `maxOutput`.
- **Точные токенизаторы для каждой модели.** В закрытом контуре их может не быть; калибровка даёт
  достаточную точность.
- **Одни пороги для всех моделей и фаз.** Противоречит оговорке ADR-0001 о настройке по модели.
