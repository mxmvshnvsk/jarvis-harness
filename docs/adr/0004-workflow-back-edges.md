# ADR-0004: Обратные рёбра workflow и ограниченные итерации

- Статус: принято
- Дата: 2026-10-03
- Основание: [ADR-0001](0001-target-architecture.md) §5 (SDD pipeline, «workflow policy решает, какие ветки
  обязательны»), §6 (агенты и схемы результата), §7 (reset между фазами), §11 (бюджет), принцип
  «Workflow owns control»
- Код (план): `src/core/workflow.ts` (граф шагов, `transitions`), `src/orchestration/runtime.ts` (выбор
  перехода, счётчики), `src/workflows/sdd.yaml` (стандартные обратные рёбра), `src/agents/*/schema.ts`
  (поле `outcome`), события `workflow.loop` в telemetry

## Контекст

Pipeline в ADR-0001 линейный: research → spec → impact → plan → implementation → review. Policy умеет только
пропускать фазы. На legacy-коде impact analysis регулярно обнаруживает то, что требует вернуться в
research (неизвестная подсистема, недокументированное бизнес-правило), review — вернуться в plan, а не
только в implementation. Без явных обратных рёбер агент либо «дорабатывает на месте» (накапливает контекст,
против §7), либо Run падает, и человек перезапускает его с нуля, теряя артефакты. Без ограничения итераций
обратные рёбра — способ сжечь квоту по кругу.

## Решение

### 1. Workflow — направленный граф с объявленными переходами

```
Step
  |- id, kind (deterministic | agentic | approval | composite)
  |- agent?            для agentic
  |- inputs[]          типы артефактов, которые шаг получает
  |- outputs[]         типы артефактов, которые шаг обязан произвести
  `- transitions
       |- onSuccess:            <stepId> | DONE
       |- onFailure:            <stepId> | FAIL
       `- onOutcome:
            <outcome>: { to: <stepId>, maxIterations: n }
```

Переходы объявляются в определении workflow. Агент не выбирает, куда идти: он заполняет поле `outcome` в
своём артефакте (валидируется Zod-схемой агента), а runtime применяет переход детерминированно. Это
сохраняет принцип «workflow owns control»: цикл существует только там, где его разрешил автор workflow.

### 2. Outcome — часть схемы артефакта

У каждого агента, из шага которого есть обратное ребро, схема результата содержит:

```
outcome:  "ok" | <перечисление, объявленное workflow>
reasons[]: { kind, summary, sourceRefs[] }     обязательно при outcome != "ok"
```

`reasons` — структурированный вход для шага, в который возвращаемся: не «попробуй ещё раз», а «неизвестно,
как обрабатывается X, см. файл Y».

### 3. Счётчики и исчерпание

Run хранит `iterations: { [edgeId]: n }`. Переход по обратному ребру увеличивает счётчик; при
`n > maxIterations` runtime **не** переходит и **не** падает молча: Run получает артефакт
`loop-exhausted.json` (ребро, итерации, все `reasons` по итерациям) и переходит в `WAITING_HUMAN`. Человек
может поднять лимит для этого Run (`jarvis resume --allow-iteration <edgeId>`), изменить spec или отменить.

По умолчанию `maxIterations: 2`; для fix-loop `review → implementation` — 3 (он уже был в ADR-0001).

### 4. Контекст и артефакты при возврате

Возврат в фазу — это новая итерация шага с reset контекста (ADR-0001 §7): агент получает чистое окно,
свои входные артефакты, **предыдущую версию своего артефакта** и `reasons`. Предыдущие версии не теряются —
артефакты версионируются (ADR-0005), ссылки в trace указывают на конкретную версию. `stepHistory[]` в Run
фиксирует каждую итерацию: `{ stepId, iteration, startedAt, finishedAt, outcome, artifactVersions }`.

### 5. Бюджет

Перед переходом по обратному ребру Budget Manager проверяет остаток квоты против оценки стоимости итерации
(медиана прошлых итераций этого шага в этом Run, иначе — оценка из policy). Недостаточно — `WAITING_BUDGET`,
а не старт итерации, которая упрётся в лимит посередине.

### 6. Стандартные обратные рёбра SDD-workflow

| Откуда | Куда | Outcome | maxIterations |
| --- | --- | --- | --- |
| impact | research | `needs_research` — найдены неизвестные области/правила | 2 |
| plan | spec | `spec_infeasible` — требования противоречат коду или друг другу | 1 |
| tests / metrics / telemetry | implementation | `defects_found` | 2 |
| review | implementation | `fix_required` | 3 |
| review | plan | `plan_wrong` — проблема не в коде, а в подходе | 1 |

Каждый такой возврат порождает событие `workflow.loop` в telemetry (ребро, итерация, причины) — это
метрика качества research/spec для evals: много `needs_research` — слабый discovery.

### 7. Что остаётся запрещённым

- Рёбра, не объявленные в workflow, — агент не может «попросить» переход.
- Циклы без `maxIterations` — валидация workflow-определения отвергает их при загрузке.
- Параллельные ветки с обратными рёбрами внутрь другой ветки — не поддерживаются; возврат возможен только в
  шаги на пути до точки ветвления.

## Последствия

- Модель Step и формат workflow-определения расширяются до запуска v0.1 workflow (этап 7 roadmap) —
  дешевле, чем переделывать линейный runtime потом.
- У агентов появляется дисциплина: «не могу продолжать» — это структурированный outcome, а не текст в
  артефакте.
- Trace становится честнее: видно, сколько итераций и почему; evals получают сигнал о качестве ранних фаз.
- Усложняется UI статуса (`jarvis status`): показывает итерации и причины возвратов.

## Альтернативы

- **Свободное планирование агентом (swarm/ReAct над всем workflow).** Отвергнуто ADR-0001: неконтролируемый
  расход и неповторяемость.
- **Линейный pipeline + ручной перезапуск.** Теряет артефакты и контекст, перекладывает цикл на человека;
  именно от этого Jarvis должен избавлять.
- **«Доработка на месте» внутри шага без возврата.** Нарушает reset между фазами, растит контекст, прячет
  проблему research внутри impact.
