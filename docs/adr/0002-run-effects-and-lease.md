# ADR-0002: Гарантии исполнения Run — журнал эффектов и аренда

- Статус: принято
- Дата: 2026-10-03
- Основание: [ADR-0001](0001-target-architecture.md) §4 (состояния Run), §12 (checkpoints), §19 («Process
  killed → resume с последнего durable checkpoint»), §21 («Run переживает завершение процесса, quota wait и
  ручное resume без потери состояния»)
- Код (план): `src/core/run.ts` (поля аренды, состояние `CANCELLED`), `src/storage/effects.ts` (журнал),
  `src/tools/router.ts` (проверка журнала и аренды перед эффектом), `src/orchestration/lease.ts`,
  `src/orchestration/scheduler.ts` (auto-resume только по истёкшей аренде), CLI `jarvis resume|cancel`

## Контекст

ADR-0001 обещает, что Run переживает kill процесса и продолжается с checkpoint. Это верно только для шагов
без побочных эффектов. Шаг, который успел оставить комментарий в Jira, сделать `git push`, создать PR или
перевести задачу в другой статус, при повторе после resume выполнится второй раз. Checkpoint фиксирует
состояние Run, но не знает, что успело произойти во внешних системах между checkpoint и падением.

Вторая проблема: один и тот же Run может возобновить daemon (auto-resume после восстановления квоты) и
разработчик (`jarvis resume <run>`), и ничто не мешает им сделать это одновременно. Два процесса, пишущие в
один Run, — потеря состояния и двойные эффекты.

## Решение

### 1. Классификация действий

Каждая capability в Tool Registry (ADR-0001 §9) получает признак `effect`:

| Класс | Примеры | Повтор после resume |
| --- | --- | --- |
| `pure` | model call, `repo.search`, `repo.read`, `jira.get`, typecheck, tests | допустим, стоит только квоты/времени |
| `effect` | `jira.comment`, `jira.transition`, `git.push`, `bitbucket.pr.create`, любая запись через MCP | **недопустим без журнала** |

Запись файлов внутри workspace Run — отдельный случай: workspace является git worktree (ADR-0003), и
checkpoint — это commit. При resume worktree сбрасывается на commit checkpoint'а, поэтому файловые записи в
журнал не попадают.

### 2. Журнал эффектов

Таблица `effects` в `jarvis.db`:

| Поле | Смысл |
| --- | --- |
| `id` | UUID |
| `run_id`, `step_id`, `iteration` | к какому шагу относится (итерация — ADR-0004) |
| `key` | idempotency key: `sha256(runId, stepId, iteration, capability, normalizedArgs, seqInStep)` |
| `capability` | нормализованное имя, например `jira.comment` |
| `args_ref` | ссылка на blob с аргументами (после редакции секретов, ADR-0010) |
| `lease_epoch` | эпоха аренды, под которой эффект выполнялся (§5) |
| `status` | `intended` → `done` \| `failed` \| `unknown` |
| `result_ref` | blob с результатом (id созданного комментария, sha, URL PR) |
| `created_at`, `finished_at` | |

Протокол в Tool Router для `effect`-capability:

1. Вычислить `key`. Если в журнале есть `done` с этим ключом — вернуть сохранённый результат, провайдера не
   вызывать.
2. Если есть `intended`/`unknown` — исход неизвестен (процесс упал между вызовом и записью). Вызвать
   `verify(key, args)` провайдера (§3). Нашёл — записать `done` и вернуть; точно не нашёл — выполнить заново;
   не может установить — перевести Run в `WAITING_HUMAN` с артефактом `effect-unresolved.json`
   (что пытались сделать, где искать следы).
3. Иначе записать `intended`, выполнить, записать `done` или `failed` (с ошибкой провайдера).

Запись `intended` и проверка аренды (§5) происходят в одной SQLite-транзакции.

### 3. Маркеры во внешних системах

Каждый эффект, оставляющий текст во внешней системе (комментарий, описание PR, commit message), получает
маркер `jarvis:run=<runId> effect=<key[0:12]>` — в footer комментария или trailer коммита. `verify()`
провайдера ищет маркер: для Jira — поиск комментариев задачи по маркеру, для git — `git ls-remote` ветки и
trailer в коммите, для Bitbucket — PR по ветке и маркеру. Провайдер без `verify` обязан объявить capability
как `effect: { verifiable: false }`; такие capability политика по умолчанию разрешает только при
`WAITING_HUMAN`-подтверждении после resume.

### 4. Гранулярность checkpoint и агентные шаги

Checkpoint делается на границе шага и, для agentic-шагов, каждые `N` tool calls (значение из policy, по
умолчанию 5). Intra-step checkpoint сохраняет список выполненных tool calls и их результаты (ссылки на
artifact store), чтобы при resume агент не повторял чтение, а получил результаты из хранилища. Модельные
вызовы не журналируются: они `pure`, их повтор — только цена квоты.

Итог: журналируемые эффекты выполняются effectively-once; всё остальное — at-least-once.

### 5. Аренда Run

Поля в `runs`: `lock_owner` (`cli:<host>:<pid>` \| `daemon:<host>` \| `ci:<pipelineId>`), `lock_epoch`
(целое, растёт при каждом захвате), `lock_until`. Параметры: heartbeat 30 с, TTL 90 с.

- Захват — compare-and-set одним `UPDATE … WHERE id = ? AND (lock_until IS NULL OR lock_until < now())`;
  успех — одна изменённая строка, `lock_epoch += 1`.
- Heartbeat продлевает `lock_until` только при совпадении `lock_epoch`; несовпадение означает, что аренду
  забрали — процесс завершает текущий шаг без новых эффектов и выходит с кодом `13` (lease lost).
- Tool Router перед каждым `effect` сверяет `lock_epoch` Run с эпохой своего процесса (fencing): эффект под
  устаревшей эпохой отвергается до вызова провайдера, запись в журнал получает `lease_epoch`.
- Daemon берёт только Run без аренды или с истёкшей. `jarvis resume` при живой аренде отказывает с указанием
  владельца; `--force` допустим только с истёкшей арендой либо с явным `--steal`, который пишется в audit
  trail с актором (ADR-0006).

### 6. Отмена

Добавляется терминальное состояние `CANCELLED` (ADR-0001 §4 его не содержит): `jarvis cancel <run>` ставит
`cancel_requested`, владелец аренды завершает текущий шаг на ближайшей безопасной точке (до следующего
эффекта), делает checkpoint и переводит Run в `CANCELLED`. Без живой аренды переход выполняется сразу.
Внешние эффекты не откатываются — у Run есть журнал, что было сделано; откат — отдельное человеческое
решение.

## Последствия

- Resume безопасен для Jira/git/Bitbucket; требование §21 ADR-0001 становится выполнимым, а не декларативным.
- Каждый MCP/local provider с write-capability обязан реализовать `verify()` или объявить себя
  непроверяемым. Это критерий приёмки провайдера.
- Маркеры видны людям в Jira и в git-истории. Это осознанно: они же — часть provenance (ADR-0001 §14).
- Журнал — ещё один источник для trace «почему Jarvis изменил эту строку»: цепочка доходит до конкретного
  внешнего эффекта.
- Аренда добавляет поведение «процесс сам выходит, если его обогнали» — его нужно покрыть тестом с двумя
  процессами на одной SQLite.

## Альтернативы

- **Resume средствами Mastra.** Восстанавливает состояние workflow, но не знает о внешних эффектах и не
  дедуплицирует их; проблема остаётся.
- **Saga с компенсациями.** Компенсация комментария или transition в Jira не всегда существует и всегда
  шумит для людей. Проверка-перед-повтором проще и не оставляет следов.
- **Файловые локи вместо аренды в БД.** Не работают между daemon, CLI и CI на разных машинах при будущем
  shared backend; аренда в RunStore переезжает вместе с хранилищем.
