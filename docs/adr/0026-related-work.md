# ADR-0026: Смежная работа — ветки и PR связанных задач как источник спеки

- Статус: принято; сделано 2026-10-21: шаги `related-work` и `related-check`, опция прогона `related`,
  capability `jira.devInfo`, `bitbucket.branch.list|commits`, `bitbucket.commit.get`, `bitbucket.file.get`
- Дата: 2026-10-21
- Основание: [ADR-0025](0025-knowledge-repo-and-cross-service-tasks.md) (карта сервисов, каталог контрактов,
  проверка полей DTO), [ADR-0017](0017-models-and-mcp-configuration.md) (профили MCP),
  [ADR-0016](0016-egress-policy.md) (сети), [ADR-0019](0019-human-collaboration.md) (зависимости и открытые
  вопросы спеки); пилот: фронтовая задача, у которой бэк уже сделан в ветке задачи, но не влит в dev
- Код (план): `src/sources/relatedWork.ts` (сбор), шаг `related-work` во встроенных workflow, профильные
  capability `jira.devInfo`, `bitbucket.branch.list`, `bitbucket.file.get`, документ `related-work`

## Контекст

Задача на фронт описывает экран, а контракт бэка для него уже написан — в ветке бэковой задачи того же эпика,
ещё не влитой в dev. Research смотрит в dev своего и соседнего репозитория, контракта там нет, и спека либо
выдумывает поля, либо спрашивает человека о том, что уже есть в коде. Человек в такой ситуации открывает
эпик, бэковую задачу, её PR и читает дифф.

У команды пилота для этого есть всё, что нужно машине:
- ветка и коммит всегда несут ключ задачи (регламент `git cz` не пропускает коммит без него);
- эпик содержит стори и задачи, у которых тип говорит о стороне: Back Task (у части команд — Middle Task), Front Task, иногда просто Task;
- в задаче Jira связаны её ветки, коммиты и PR (панель Development);
- у бэкендера склонированы почти все репозитории, у фронтендера бэковых обычно нет.

## Решение

### 1. Шаг без модели, не агент

Найти связанные задачи, их ветки и PR, взять дифф и выбрать из него контракт — механика. Её делает
детерминированный шаг `related-work` после `sources`; модель (research, затем spec) получает готовый документ и
решает, что из него следует для задачи. Отдельный агент «repo researcher» не нужен: он листал бы Bitbucket
медленнее и дороже скрипта, а понимание у research уже есть.

### 2. Какие задачи смежные

От задачи прогона:
1. эпик и родитель (стори) — через `jira.get`;
2. соседи по эпику и стори — `jira.search` (`"Epic Link" = X OR parent = X`), не больше 30;
3. явные ссылки задачи (blocks, relates to, is implemented by).

Порядок интереса: задачи другой стороны (для Front Task — Back Task, Middle Task и Task), потом остальные. Задача в статусе
Done, чья ветка влита, интересна только своим коммитом в dev — её изменения уже видны research как код.

### 3. Где их работа

По задаче — её ветки и PR, первым найденным способом:
1. **Jira, панель Development** (`jira.devInfo`): ветки, PR и их статусы, репозиторий. Самый точный путь —
   связь уже сделана людьми и регламентом.
2. **Локальный git**, если репозиторий сервиса склонирован (карта сервисов знает путь): `git fetch` и ветки
   `*<KEY>*` на remote. Быстро и без MCP — обычный случай у бэкендера.
3. **Bitbucket MCP**: `bitbucket.pr.list` с ключом в заголовке или ветке, `bitbucket.branch.list` с фильтром.
   Обычный случай у фронтендера.

Если ничего не нашлось — в документе так и написано («у ABC-41 нет ни ветки, ни PR»), это тоже факт для спеки.

### 4. Что в ней сделано

Дифф ветки против её базы (`merge-base` с dev) — локально `git diff`, иначе `bitbucket.pr.diff` или
`bitbucket.file.get` для файлов контракта. Из диффа берётся только то, что важно смежнику:
- контракт: эндпоинты, DTO и их поля, события и их payload — тем же разбором, что проверка контракта
  ADR-0025 §6 (Java, Kotlin, TypeScript), плюс OpenAPI/AsyncAPI, если файл в диффе;
- миграции и фича-флаги — именами;
- остальное — списком файлов с числом строк, без текста.

Объём ограничен: до 12 задач (`maxIssues`), сначала связанные и названные в задаче, до 40 файлов контракта на задачу; лишнее — ссылкой «прочитать по запросу».

### 5. Документ `related-work`

```json
{
  "items": [{
    "issue": "ABC-41", "type": "Back Task", "status": "In Review",
    "service": "orders-api",
    "branch": "feature/ABC-41-discount", "commit": "a1b2c3d", "base": "dev",
    "pr": { "id": 312, "state": "OPEN", "url": "…" },
    "found": "jira-dev-info",
    "contract": [{ "kind": "dto", "name": "OrderDto", "fields": [{ "name": "discountAmount", "change": "added", "type": "number" }] }],
    "files": { "contract": 3, "other": 12 }
  }],
  "notFound": ["ABC-43"]
}
```

Research и spec получают его входом. Правило в их инструкциях: опора на неслитую ветку — **зависимость**, не
факт. Спека записывает её в `dependencies` с задачей, веткой, коммитом и статусом PR («бэк в ABC-41, коммит
a1b2c3d, PR открыт, добавляет `OrderDto.discountAmount`») и не выдумывает того, чего в ветке нет.

### 6. Ветка может уехать

Перед `implementation` и на `review` шаг сверяет: тот же ли коммит у ветки, влит ли PR, не изменился ли
контракт. Влита без изменений — зависимость закрыта. Ушла вперёд с изменением контракта — предупреждение в
ленте и вход для review с разницей; на гейте спеки это видно человеку. Без доступа к репозиторию в этот момент
— пометка «не проверено», прогон не падает.

### 7. Доступы и сеть

Bitbucket и Jira в профиле `intranet`, для `confidential` это допустимо (ADR-0016). Чтение диффа чужого
репозитория — то же чтение, что `jira.get`: без эффектов. Через MCP читаются только файлы из диффа ветки, не
весь репозиторий. Секреты из диффа проходят Redactor, как любой вывод инструмента.

### 8. Включено или нет — решает человек, на прогон

Поиск смежной работы необязателен, как автономный режим, — тем же устройством:
- **на прогон:** `jarvis work|spec|fix … --related` / `--no-related`; в «Новой задаче» — галочка «Смотреть смежные
  задачи и их ветки» в «Ещё настройки». Она стоит, когда в проекте поиск включён по умолчанию, и снимается для
  этой задачи (например, задача не связана с другими или нужен быстрый прогон);
- **по умолчанию для проекта:** `relatedWork.enabled`;
- выбор хранится в прогоне (опция `related`) и переходит в продолжение (spec → sdd), перезапуск и сабтаски;
- выключенный шаг пропускается с причиной «off for this run», в ленте это видно; сверка ветки (§6) тоже не
  делается — нечего сверять.

```yaml
relatedWork:
  enabled: true                # по умолчанию для прогонов проекта; без Jira шаг пропускается сам
  maxIssues: 12
  sides:                       # тип задачи Jira → сторона; для подбора «другой стороны»
    "Back Task": back
    "Middle Task": back        # так бэковую задачу зовут у части команд
    "Front Task": front
  base: dev                    # с чем сравнивать ветку; по умолчанию — ветка по умолчанию репозитория
```

### 9. Story между эпиком и задачами

У части команд в эпике лежат Story, а задачи входят в Story связью «Включение» (со стороны Story —
«Включает в себя», со стороны задачи — «Включена в»). У Story своя ветка `feature/<KEY>` от dev, в каждом
репозитории, который она трогает, с одинаковым именем. Ветки задач создаются от неё, PR задач идут в неё,
а PR Story идёт в dev после проверки на стенде. Настройки — `relatedWork.story`: типы, имена связи и
шаблон ветки.

- **Соседи.** Сначала идут задачи своей Story, другая сторона раньше своей, затем сама Story, затем
  связанные задачи и остальные задачи эпика. Эпик берётся у задачи, а если его там нет — у Story.
- **С чем сравнивать.** Ветка задачи сравнивается с `destination` её PR, иначе с веткой Story в том же
  репозитории. Story сравнивается с базой. Каждая пара «репо + ветка» — отдельный пункт: Story может быть
  уже в dev в одном репо и ещё нет в другом.
- **Влита в Story — ещё не в dev.** Задача, влитая в ветку Story, отмечается так, пока не влит PR самой
  Story. `related.check` читает ветки по тем же правилам.
- **База прогона.** Если в репо прогона есть ветка Story (`story.base`, по умолчанию да), прогон задачи
  начинается от неё и PR идёт в неё. Если ветки ещё нет — обычная база и предупреждение в ленте. Явный
  `--base` важнее. Задача без Story работает как раньше: оба режима живут в одном эпике.
- **Сторона задачи.** Сначала по типу (`sides`), затем по префиксу в названии (`prefixes`: `[Java]`,
  `[Front]`, … без учёта регистра). Нужно для команд, у которых все задачи — `Change`.

## Что есть у MCP-серверов (проверено 2026-10-21)

Инструменты серверов пилота (`mcp-atlassian`, Bitbucket Server MCP) покрывают все три пути §3:

| Нужно | Инструмент | Capability профиля |
|---|---|---|
| ветки, PR, коммиты задачи (панель Development) | `jira_get_issue_development_info`, пачкой — `jira_get_issues_development_info` | `jira.devInfo` |
| эпик и его задачи | `jira_get_project_epic_hierarchy`, `jira_search` | `jira.epic`, `jira.search` |
| связи между проектами | `jira_get_cross_project_dependencies` | `jira.dependencies` |
| ветки репозитория, одна ветка | `list_branches`, `get_branch` | `bitbucket.branch.list`, `bitbucket.branch.get` |
| коммиты ветки, коммит с файлами | `list_branch_commits`, `get_commit_detail` | `bitbucket.branch.commits`, `bitbucket.commit.get` |
| файл на ветке | `get_file_content` | `bitbucket.file.get` |
| PR и его дифф | `list_pull_requests`, `get_pull_request`, `get_pull_request_diff` | есть |

Дифф ветки без PR: коммиты ветки после её базы (`list_branch_commits` до коммита dev) → файлы из
`get_commit_detail` → файлы контракта читаются `get_file_content` на ветке и на базе и сравниваются. Все
инструменты — чтения; эффекты сервера (`create_pull_request`, `merge_pull_request`, `delete_branch`) профиль
агентам не выдаёт.

## Последствия

- Спека фронта опирается на реальный контракт бэка из его ветки, с явной отметкой, что он ещё не влит.
- Меньше вопросов человеку о том, что уже есть в коде соседей.
- Ещё один шаг до research: секунды локально, до десятков секунд через MCP; без Jira шаг пропускается.
- Сверка в §6 ловит расхождение до ревью кода, а не после влития.

## Альтернативы

- **Агент repo-researcher с инструментами Bitbucket.** Гибче, но дорого и недетерминированно: тот же сбор
  разный от прогона к прогону, а слабая модель путается в листинге веток.
- **Ждать влития в dev.** Так сейчас, и спека фронта отстаёт на ревью бэка.
- **Только локальный git.** Не работает у фронтендера, у которого нет бэковых репозиториев.
