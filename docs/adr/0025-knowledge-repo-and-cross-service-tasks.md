## Контекст

Бэкенд — десятки микросервисов, каждый в своей репе. Сейчас Jarvis живёт в одной репе: там `.jarvis/project.yaml`,
знание `.jarvis/knowledge`, прогон работает в копии этой репы. Для бэкенда этого мало:
- знание должно быть сквозным: границы сервисов, кто отдаёт эндпоинт или топик и кто его потребляет, общий
  глоссарий;
- в репах сервисов не должно быть ничего от Jarvis: ни `.jarvis`, ни сгенерированных документов;
- задача часто задевает несколько сервисов: новое поле в событии меняет того, кто его шлёт, и тех, кто читает.

Команда платформы ведёт отдельную репу знаний. Изменения в неё идут через PR, конфликты решают люди. Репы у
разработчиков лежат рядом, в одной папке, но не у всех одинаково.

## Решение

### 1. Мета-репа — единственное место Jarvis

```
repos/
  jarvis-knowledge/            # мета-репа: владеет команда, изменения через PR
    project.yaml               # общее для всех сервисов + карта сервисов (§2)
    workflows/
    knowledge/
      landscape.md             # границы: домены, сервисы, владельцы — пишут люди
      glossary.md
      services/
        orders-api/            # знание сервиса: architecture, conventions, contracts, module-*.md
          contracts.json       # машинная часть contracts.md (§4)
        delivery-slots-api/
    evals/
  orders-api/                  # репы сервисов — без .jarvis
  delivery-slots-api/
  notify-api/
```

Репа только для Jarvis, поэтому его файлы лежат в её корне; `.jarvis/` внутри тоже поддерживается и тогда
главнее. `project.yaml` в корне считается файлом Jarvis, только если в нём есть `version` и `services:`. Создать
такую репу с черновиком карты: `jarvis init --knowledge` (по git-репам рядом; код не читается).

Всё, что Jarvis сейчас пишет в `.jarvis` репы (`onboard`, принятые модули, термины глоссария), пишется в мета-репу,
в `knowledge/services/<сервис>/`. Сам Jarvis в мета-репе не коммитит: страница и `jarvis status` показывают, что в
её рабочей копии изменено, и дают команду для ветки и PR. Сгенерированное (`contracts.*`, скан) пишется
детерминированно и отсортированно, по файлу на сервис, чтобы PR от разных людей реже конфликтовали.

Режим одной репы со своей `.jarvis` остаётся: мета-режим включается, когда в репе `.jarvis` нет.

### 2. Карта сервисов и конфигурация

```yaml
# jarvis-knowledge/project.yaml
version: 1
# ключи верхнего уровня — общее для всех сервисов (как project.yaml сейчас)
stack: [java, spring, mongo, kafka, gradle]
tools: { local: { test: ./gradlew test } }
workspace: { mode: worktree, checkout: clone, setup: ./gradlew classes testClasses -q }
repos: ..                       # где лежат репы; по умолчанию — папка над мета-репой
services:
  orders-api: {}                # репа ../orders-api (по имени папки)
  delivery-slots-api:
    repo: slots-service         # папка называется иначе
    tools: { local: { test: "TZ=Europe/Moscow ./gradlew test" } }
  notify-api:
    stack: [kotlin, spring, kafka, gradle]
```

- Сервис ищется по имени папки в `repos`; `services.<имя>.repo` задаёт другую папку (относительно `repos`) или
  путь.
- Раскладка у разработчика своя — она в личном конфиге: `~/.jarvis/config.yaml` → `repos: { delivery-slots-api:
  ~/work/slots }`. Порядок: личная карта, затем карта мета-репы, затем имя папки.
- `services.<имя>` принимает те же ключи, что `project.yaml` (`stack`, `tools`, `workspace`, `knowledge`,
  `security`, …). Слияние: пользователь → общее мета-репы → сервис.

### 3. Как Jarvis находит мета-репу и сервис

Запуск в репе сервиса без `.jarvis`:
1. мета-репа: `JARVIS_KNOWLEDGE`, иначе `knowledgeRepo` личного конфига, иначе соседняя папка, где есть
   `project.yaml` (в корне или в `.jarvis/`) с `services:` (сначала `jarvis-knowledge`);
2. сервис: тот, чья репа по карте (§2) — эта репа (`git rev-parse --show-toplevel`);
3. не нашлось — предупреждение с подсказкой: `services.<имя папки>` в мета-репе или `repos` в личном конфиге.
   `jarvis doctor` проверяет карту целиком: каждая ли репа на месте, нет ли двух сервисов на одной папке.

Запуск в самой мета-репе — задача по сервисам (§6) или работа со знанием.

### 4. Знание сервиса и соседей

Прогону в сервисе S достаётся:
- знание S: `knowledge/services/S/**`;
- общее: `landscape.md`, `glossary.md`;
- соседи: сервисы, которые потребляют то, что отдаёт S, и те, у кого S берёт. Это карточки, а не модули целиком:
  имя, владелец, общие эндпоинты и топики.

Соседи считаются без модели. `onboard` в S пишет `contracts.json`: эндпоинты, которые S отдаёт; топики, куда шлёт и
откуда читает; HTTP-клиенты и их адреса; ключи конфига. Это то же, что сейчас собирает `codeContractsOf`. Каталог
по всем сервисам строится в памяти из всех `contracts.json` и не коммитится, так что конфликтовать нечему. Модули
чужих сервисов агент получает поиском, по запросу.

HTTP-клиент связывается с сервисом по адресу. Сервисы ходят друг к другу через балансер:
`@FeignClient(url = "http://${SERVICE_HOST}/delivery-slots-api")`, так что первый сегмент пути после хоста — имя
сервиса. Совпал с именем сервиса из карты (или с его `services.<имя>.path`, если отличается) — связь есть, а
остаток пути сверяется с эндпоинтами этого сервиса. Без модели и без списков хостов. Адрес, в котором такого
сегмента нет, остаётся связью «не опознана»; гейт `scope` (§7) на неё не опирается.

Прежде чем включать гейт `scope`, каталог меряется на 3–4 связанных сервисах: найденные связи выгружаются
списком, человек, знающий сервисы, отмечает верные, ложные и пропущенные. По цифрам решается, каким связям гейт
доверяет.

Шаг impact по каталогу видит, что задача меняет контракт (эндпоинт, топик, DTO), и пишет потребителей: «поле
`slotId` в `orders.created` читают notify-api, delivery-slots-api».

### 5. Входы прогона и evals

Прогон записывает коммит мета-репы и её незакоммиченные файлы знания так же, как сейчас `.jarvis` своей репы:
`git hash-object -w` в мета-репе, id — в `run.created`. Evals живут в мета-репе: `evals/<набор>/<кейс>/`, fixture —
`{ service, commit, knowledge: { commit, overlay } }`.

### 6. Задача по нескольким сервисам: мастер-прогон и сабтаски

Мастер-прогон ведёт задачу целиком, но в коде сервисов не работает. Работа идёт в сабтасках, по одной на сервис;
каждый сабтаск — обычный прогон sdd в своей репе.

Workflow `sdd-cross` (в интерфейсе — «sdd (cross-repos)»):

| шаг | что | кто |
|---|---|---|
| research | по landscape, каталогу и графам сервисов (чтение) | модель |
| spec | одна спека задачи, гейт | модель, человек |
| split | сервисы, которые задеты (по каталогу), и предложение разбиения: сабтаски и контракт | детерминированно + модель |
| гейт разбиения | убрать или добавить сервис, поправить текст сабтаска, порядок поставки, контракт | человек |
| spawn | сабтаски-прогоны; каждому — спека, своя часть, контракт | детерминированно |
| wait | мастер ждёт сабтаски (`WAITING_CHILDREN`) | — |
| contract-check | каждая сторона контракта в своей копии: отдающий отдаёт, потребители вызывают с теми же методом, путём, топиком и полями | детерминированно |
| гейт поставки | Apply по сервисам в порядке поставки (PR — позже) | человек |

- Артефакты split: `split.json` — сабтаски `{ key, service, task, deliverAfter[] }`; `contract.json` — изменения
  `{ kind: endpoint | topic | dto, id, change, producer, consumers[] }`.
- Сабтаски стартуют параллельно (не больше `crossRepos.maxParallel`, по умолчанию 2: квота моделей общая): контракт
  зафиксирован на гейте, и потребитель пишет код и тесты по нему, не дожидаясь поставщика. `deliverAfter` задаёт
  только порядок поставки: сначала отдающий сервис, обратно совместимо, потом потребители.
- Сабтаск — полноценный прогон: свои копия, ветка, гейты, Apply, пауза, отмена, «Run again». В нём видны мастер и
  его часть контракта.
- Сабтаск упал или отменён — мастер показывает это и даёт выбор: перезапустить сабтаск, убрать сервис из
  разбиения (вернуться к гейту), отменить задачу целиком.
- Контракт менять может только мастер. Если сабтаск понял, что контракт надо менять, он останавливается с запросом
  на изменение. Мастер показывает запрос на гейте, человек решает, и новый контракт уходит остальным сабтаскам
  заметкой (`addNote`).
  Сделано так: impact сабтаска пишет `contractChange` (`item`, `change`, `why`), шаг `scope` сабтаска паркует его
  (`WAITING_HUMAN`, `contract`) и записывает запрос в мастер. На странице мастера — блок запроса с текстом контракта,
  который можно поправить; терминал — `jarvis subtask contract <мастер> [<сабтаск>] --accept [--change …] |
  --reject [--why …]`. Принято — у `split` новая версия (правка человека), затронутые сабтаски, которые ещё идут,
  получают заметку, попросивший получает заметку и заново делает impact (исход `contract_changed`). Уже завершённые
  сабтаски не перезапускаются: команда их называет. Отклонено — попросивший получает заметку и идёт дальше по
  прежнему контракту.
  Изменение может быть кодом другого сервиса карты — чаще всего общей библиотеки, где объявлен DTO. Тогда impact
  называет его в `contractChange.owner`. Если у владельца нет сабтаска, мастер показывает это в запросе, и
  принятие добавляет его в новую версию `split` (следующий ключ, `deliverAfter` попросившего дополняется им;
  новый пункт контракта — у владельца как производителя). Новый сабтаск стартует сразу, если есть слот.
  Если владелец — библиотека (`kind: library`), попросивший не продолжается сразу: его шаг `scope` ждёт
  (`WAITING_HUMAN`, `contract`, «library …»), пока изменение библиотеки примут и опубликуют (`publish-local`)
  или её сабтаск уберут. Потом он сам возобновляется и заново делает impact с новой версией. Ветки в
  репозитории библиотеки — как у любого сабтаска: ветка Story, если задача в Story, и ветка задачи от неё.
  Чтобы библиотека попадала в разбиение сразу, а не через запрос, ресерч и split знают из каталога библиотеки
  карты и их потребителей: DTO или тип, объявленный в библиотеке, — изменение и этой библиотеки, её сабтаск
  идёт первым.
- Бюджет мастера — сумма бюджетов сабтасков, его собственные шаги считаются отдельно.
  Лимит — сумма `budget.perRun` сервисов сабтасков (записывается при старте сабтаска, до старта — из репы знаний)
  плюс выданное людьми; потрачено — по всем прогонам сабтасков, отменённые и перезапущенные тоже. Сумма
  потрачена — сабтаск не делает следующий вызов модели и встаёт на обычной остановке по бюджету (`master`);
  «ещё» на ней увеличивает его долю и сумму. Мастер показывает «потрачено из суммы» на странице и в
  `jarvis subtask list`.
- Проверка контракта в первой версии: метод, путь и топик — всегда; поля — только там, где тип объявлен явно
  (`@KafkaListener void on(OrderCreatedEvent e)`, `KafkaTemplate<String, OrderCreatedEvent>`,
  `ResponseEntity<SlotDto>`), с учётом Lombok и `@JsonProperty`. Тип не виден (`KafkaTemplate<String, Object>`,
  строка из `writeValueAsString`) — «поля не проверены», без провала.
  Сделано: тип берётся из отправителя (`KafkaTemplate<…, T>`), слушателя (`@Payload`, `ConsumerRecord<K, T>`),
  метода эндпоинта (`@RequestBody`, тип ответа) или из имени DTO в контракте; объявление ищется в копии сабтаска,
  сначала в изменённых файлах. Читаются Java (классы, record, Lombok), Kotlin (data class) и TypeScript
  (interface, type, class). По каждому полю — `same | added | removed | renamed | type changed` и «сходится /
  расхождение»: поле, которое читатель ждёт, а пишущий не шлёт, — расхождение; лишнее поле у пишущего — нет. Тип
  сравнивается так, как его видит JSON (`Long`, `number`, `Optional<Long>` — число). Тело запроса пишет потребитель,
  ответ и событие — поставщик.
- Поставка в первой версии — Apply по сервисам в порядке `deliverAfter`; создание PR — позже.
- Терминал: сабтаск — обычный прогон со своим id, `jarvis status | approve | resume <id>` работают с ним как с
  любым, status добавляет строку «subtask 2 of ABC-42 · master <id>»; `jarvis status <мастер>` показывает таблицу
  сабтасков. Управление — `jarvis subtask list <мастер>`, `jarvis subtask start | retry | drop <мастер>
  <номер|сервис>`.

Модель данных: у прогона `parent?: { runId, key }`; у мастера `waitingFor: { kind: "children" }`; событие
`run.spawned`.

### 7. Как задача становится распределённой

Человек не обязан заранее знать, что задача задевает несколько сервисов. Он выбирает обычный sdd, а Jarvis
подсвечивает распределённость в трёх местах, от дешёвого к точному. Решает всегда человек.

1. **New task, до модели.** Текст задачи сверяется с каталогом (§4) и глоссарием: имена топиков, эндпоинтов, DTO,
   сервисов, термины. Найдено два сервиса или больше, и каталог связывает их (один отдаёт, другой потребляет),
   — под полем подсказка «Похоже, задевает 3 сервиса: …» с кнопкой «Switch to sdd (cross-repos)». Сама подсказка
   ничего не переключает.
2. **После impact, в sdd.** Детерминированный шаг `scope` сразу после impact сверяет изменения с каталогом:
   - меняется то, что сервис отдаёт наружу (эндпоинт, отправка в топик, DTO), но изменение обратно совместимо и
     требования спеки не касаются других сервисов — в impact строка «потребители: …», прогон идёт дальше без
     остановки;
   - требование спеки касается поведения другого сервиса **и** каталог подтверждает связь с ним через то, что
     меняется, — гейт «Задача задевает N сервисов». На нём: **Continue as sdd (cross-repos)** — мастер-прогон
     в репе знаний получает research и одобренную спеку (`handOff`, как Continue to sdd) и начинает с `catalog`;
     текущий прогон заканчивается (CANCELLED с причиной), его сервис получает сабтаск, который заново делает
     только impact; **Только этот сервис** — прогон идёт дальше, потребители уходят отдельными задачами,
     предупреждение остаётся в отчёте `scope`.

   Модель только предлагает связь требования с сервисом: impact пишет её в `elsewhere` («R4 — notify-api»),
   подсказка об этом — в документе соседей. Без подтверждения каталогом это предупреждение, а не гейт: иначе
   слабые модели будут ошибаться в обе стороны. Терминал: `jarvis scope <run> --cross | --single [--resume]`.
3. **Из research.** Если законченный research (или spec) сервиса вместе с задачей называет два сервиса и больше,
   которые каталог связывает, продолжение предлагает «Continue to sdd (cross-repos)» с пометкой «рекомендуем»,
   рядом обычный sdd (терминал: `jarvis scope <run> --cross`). Мастер начинает со spec (после spec — с catalog).

**Простой sdd не меняется:**
- в режиме одной репы (своя `.jarvis`) каталога нет: ни подсказки, ни шага `scope`, ни гейта — шаги и события те
  же, что сейчас (шаг `scope` вставляется в sdd только у сервиса репы знаний). Схема результата impact получила
  необязательное поле `elsewhere`: кассеты evals, записанные раньше, нужно переписать (`--mode record`);
- в мета-режиме `scope` — короткий шаг без модели; пока он не нашёл подтверждённую связь, задача в одном сервисе
  идёт тем же путём, что сейчас; сабтаск задачи по сервисам его проходит сразу;
- «Только этот сервис» запоминается в прогоне: «Run again» и петли не спрашивают снова;
- workflow команды, где шага `scope` нет, работает как раньше, просто без гейта;
- регрессия: eval-кейсы sdd в одиночном режиме и в мета-режиме с одним сервисом дают те же шаги, события и
  артефакты, что до изменения.

### 8. Страницы

- **Runs:** мастер — одна строка с прогрессом «2 из 3», сабтаски раскрываются под ней.
- **Мастер-прогон:** шаги `sdd-cross`; план — сервисы и стрелки контракта; доска сабтасков: состояние, шаг, что ждёт
  человека, ветка; контракт со статусом проверки по каждой стороне; поставка.
- **Гейт разбиения:** спека слева, разбиение справа, с правкой.
- **Сабтаск:** крошки «ABC-42 › orders-api», его часть контракта, соседи по задаче.
- **New task:** в выборе репы — «All services · jarvis-knowledge»; подсказка о распределённости (§7).
- **Гейт «Задача задевает N сервисов»** на странице sdd-прогона (§7).

### 9. Безопасность

Прогон сабтаска видит свою репу и знание мета-репы, остальные сервисы — только через карточки и каталог.
`security.deniedPaths` задаётся по сервисам. В мета-репу попадает только то, что прошло редактирование секретов
([ADR-0010](0010-secret-redaction.md)), как сейчас `.jarvis/knowledge`.

## Этапы

1. Мета-репа: поиск, карта, конфиг по сервисам, знание по сервисам, запись `onboard` и модулей в мета-репу,
   входы прогона. Задачи по-прежнему в одном сервисе.
2. `contracts.json`, каталог, соседи в контексте, потребители в impact.
3. Мастер-прогон `sdd-cross`, сабтаски, проверка контракта, страницы (§8).
4. Как задача становится распределённой (§7): подсказка в New task, шаг `scope` и гейт в sdd, продолжение
   research.
5. Evals в мета-репе.

## Последствия

- В репах сервисов ничего от Jarvis; команды подключаются строкой в карте.
- Знание ревьюится как код, через PR в одну репу.
- Задача по сервисам — несколько небольших прогонов в одной репе каждый: контекст узкий, и с этим справляются
  слабые модели.
- Новое: мета-режим загрузки конфигурации, сабтаски в модели данных, проверка контракта по коду двух репозиториев.
- Без доступа к мета-репе Jarvis в сервисе работать не может. В одиночном режиме остаётся `.jarvis` в репе.

## Альтернативы

- **`.jarvis` в каждой репе сервиса.** Знание расползается по репам и ревьюится в каждой отдельно, сквозного
  каталога нет; команда не хочет файлов Jarvis в сервисах.
- **Один прогон на несколько реп.** Копии и тесты всех сервисов в одном контексте: на слабых моделях не работает,
  Apply и откат размазаны по репам.
- **Каталог контрактов как закоммиченный файл.** Каждый `onboard` правил бы один общий файл, и PR конфликтовали
  бы. Каталог строится из файлов по сервисам.
- **Монорепо или git submodules.** Меняют то, как команды работают с кодом, ради инструмента.
