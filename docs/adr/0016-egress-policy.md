# ADR-0016: Egress policy — классы данных, приватные модели и сетевые инструменты

- Статус: принято (taint tracking — «На будущее», отдельным решением после v0.4)
- Дата: 2026-10-03
- Основание: [ADR-0001](0001-target-architecture.md) §1 («закрытая корпоративная среда, где модели не
  имеют доступа в интернет»), §9 (Tool Registry, Tool Router выдаёт разрешённый subset), §10 (Model Router
  по роли и политике), §13 («Policy Engine должен быть детерминированным»); [ADR-0007](0007-model-capabilities.md)
  §1 (дескриптор модели), §3 (проверка совместимости при создании Run); [ADR-0005](0005-artifact-versions-provenance.md)
  (`sourceRefs`, provenance), [ADR-0010](0010-secret-redaction.md) §3 (экспорт telemetry как канал egress)
- Код (план): `src/core/config/schema.ts` (`dataClass`), `src/models/registry.ts` (`egress`),
  `src/tools/registry.ts` (`network`), `src/security/policy/egress.ts` (правило), `src/context/layers.ts`
  (метка `untrusted` для интернет-результатов), `jarvis doctor` (строка egress), `jarvis work` (проверка
  при создании Run)

## Контекст

ADR-0001 исходит из закрытого контура: модели — за корпоративным endpoint'ом, интернета нет. Но Jarvis —
открытый проект, и тот же пакет будет работать на личных и OSS-проектах, где облачные модели и интернет
уместны. Внутри корпорации тоже есть градации: исследование публичной библиотеки не обязано идти через
приватный кластер. Без явной политики граница держится на привычке, а ошибка здесь необратима: контекст
с кодом и текстом Jira, однажды отправленный в облако, не отзывается.

Два разных риска, которые нельзя смешивать:

| Канал | Что уходит наружу | Что приходит | Риск |
| --- | --- | --- | --- |
| модель (ContextPackage → endpoint) | весь контекст шага: код, Jira, Confluence, артефакты | ответ модели | утечка корпоративных данных |
| инструмент (web search, fetch, registry) | текст запроса | недоверенный контент | утечка терминов запроса; prompt injection |

«Исследованию можно в интернет» почти всегда означает второе. Для первого это неверно: research-агент
держит в контексте текст задачи.

## Решение

### 1. Три метки

**Проект** — `.jarvis/project.yaml`:

```yaml
dataClass: confidential      # public | internal | confidential; по умолчанию confidential
```

Если поле не задано, проект считается `confidential` — безопасный дефолт для корпоративного контура.
Личный/OSS-проект объявляет `public` явно.

**Модель** — дескриптор (ADR-0007 §1):

```yaml
models:
  deepseek-flash:
    egress: private          # private — контур организации; cloud — внешний провайдер
```

Поле обязательное; модель без `egress` не загружается. `private` означает, что endpoint находится внутри
контура организации, — это утверждение администратора конфига, Jarvis его не проверяет (не может), но
записывает источник значения (`config show --sources`, ADR-0014).

**Capability** — Tool Registry:

```
network: none | intranet | internet
```

Локальные инструменты (fs, git, AST, tests) — `none`. MCP-провайдеры корпоративных систем — `intranet`.
Web search, fetch произвольных URL, публичные registry — `internet`. Провайдер объявляет значение;
capability без него — `internet` (худший случай).

### 2. Правило

Детерминированное, в Policy Engine, без участия модели:

| `dataClass` проекта | Допустимые модели | Допустимые инструменты |
| --- | --- | --- |
| `confidential` | `egress: private` | `network: none \| intranet` |
| `internal` | `egress: private` | `network: none \| intranet` + `internet` с ограничениями §4 |
| `public` | любые | любые |

Разница `internal`/`confidential` — только в интернет-инструментах: `internal` допускает поиск по
публичным источникам (запрос уходит наружу), `confidential` — нет. Модели для обоих — только приватные.

Проверка выполняется при создании Run для всех шагов workflow — вместе с проверкой совместимости моделей
(ADR-0007 §3): workflow, которому нужна недопустимая модель или capability, не стартует. На шаге Tool
Router дополнительно отвергает любую capability, не прошедшую правило (защита от динамически
подключённых провайдеров), с событием `security.egressDenied`.

Политика проекта может только ужесточать (`internal` → `confidential` для ветки/задачи через профиль), но
не ослаблять: `dataClass` переопределяется только вверх, расширение через env/флаги запрещено схемой.

### 3. Остальные каналы

- Экспорт telemetry — уже ограничен ADR-0010 §3 (payload'ы выключены по умолчанию); адрес backend'а
  экспорта обязан быть `intranet` для `confidential`/`internal`.
- Бандлы (ADR-0009 §5) — файлы, их перемещение вне контура — ответственность человека; `jarvis export`
  печатает `dataClass` проекта в заголовке манифеста и предупреждение.
- Эмбеддер (ADR-0015 §4) — та же метка `egress`, что у моделей; для `confidential` только `private`.
- Кэш моделей `probe` (ADR-0007) — канареечные запросы содержат только синтетику, но идут на endpoint;
  `probe` для `cloud`-моделей в `confidential`-проекте не выполняется.

### 4. Интернет-инструменты как недоверенный вход

Результаты capability с `network: internet` попадают в контекст только в слой L4 с меткой
`untrusted: true` и префиксом-обёрткой, отделяющей их от инструкций. Policy: шаг, в контексте которого есть
`untrusted`-источники, не может инициировать `effect`-capability (ADR-0002 §1) без human gate; такой
источник в `sourceRefs` артефакта помечается, и это видно в trace. Это защита от инъекции через
загруженную страницу, а не от утечки.

### 5. Наблюдаемость

`jarvis doctor` печатает одну строку: `egress: dataClass=confidential; models=private only (3);
tools=none|intranet (12 allowed, 4 denied); telemetry export=intranet`. `jarvis status` показывает
`dataClass` Run. Событие `security.egressDenied` в telemetry — с именем capability/модели, без данных.

## Последствия

- Граница контура — правило в коде, а не привычка; проверяется до старта Run и при каждом вызове.
- Один и тот же пакет работает в корпорации (`confidential`) и дома (`public`) без форков и флагов.
- Безопасные дефолты: проект без метки — `confidential`, capability без метки — `internet`, модель без
  метки — ошибка.
- Цена — три поля и одно правило; требования к провайдерам: объявлять `network`.

## На будущее

**Taint tracking по источникам.** Каждый артефакт и слой контекста наследует максимальный `dataClass`
своих `sourceRefs` (ADR-0005): задача из Jira — `confidential`, имя публичной библиотеки и текст ошибки
без корпоративных путей — `public`. Агент, чей ContextPackage содержит только `public`-источники, может
использовать `cloud`-модель и `internet`-инструменты даже в `confidential`-проекте — это и есть сценарий
«исследование публичной библиотеки». Требует: классификации источников при импорте (Jira/Confluence —
всегда класс проекта; код — класс проекта; результаты интернет-инструментов — `public`), проверки Redactor'ом
отсутствия корпоративных идентификаторов в «чистом» контексте, и evals (ADR-0012), показывающих, что доля
задач с выигрышем от облачной модели оправдывает сложность. Рассматривается после v0.4.

## Альтернативы

- **Ничего не делать: «в контуре интернета всё равно нет».** Верно для одного контура и неверно для OSS-
  использования и для будущих моделей; первая же `cloud`-модель в конфиге без правила — утечка.
- **Сетевая изоляция на уровне ОС/прокси.** Нужна и не отменяется, но Jarvis не должен на неё полагаться:
  он работает на машинах разработчиков, где прокси настроен по-разному.
- **Taint tracking сразу.** Правильная конечная точка, но требует классификации всех источников и
  evals; статическое правило закрывает риск сейчас и совместимо с taint позже.
