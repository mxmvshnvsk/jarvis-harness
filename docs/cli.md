# Справочник CLI

`jarvis [--json] [--profile <name>] [--cwd <dir>] [--color|--no-color] [--progress <mode>] <command>`

Глобальные опции:

| Опция | Действие |
|---|---|
| `--json` | машинно-читаемый вывод (одна JSON-структура вместо текста) |
| `--profile <name>` | применить профиль из `profiles:` конфигурации (ADR-0009 §1); профиль может только сужать |
| `--cwd <dir>` | работать так, будто команда запущена из `<dir>` |
| `--color` / `--no-color` | раскрашивать вывод и вне терминала / не раскрашивать никогда |
| `--progress auto\|tty\|plain\|json` | как показывать ход прогона в stderr (ниже, «Терминал: что видно по ходу прогона») |
| `-V`, `--version` | версия и коммит, из которого собран CLI |

Оформление вывода (`src/cli/style.ts`) одно на все команды, по соглашениям git, gh и cargo:
заголовки жирные; то, о чём строка (кандидат, прогон, стандарт), — жирным голубым; служебное (id,
время, подписи полей, пояснения) — тусклым; команды для ввода — голубым (любой текст в обратных
кавычках); успех и добавленные строки — зелёным, предупреждения и «проверить» — жёлтым, ошибки и
удалённые строки — красным; содержимое — цветом терминала. `jarvis diff` красит дифф как git,
`candidates show` подсвечивает markdown документа. Ошибки начинаются с `error:` и идут в stderr,
туда же уведомления (`⚠` повтор, `✗` отказ). Цвет включён только для терминала и никогда в `--json`;
решают по порядку `--color`/`--no-color`, `NO_COLOR` (no-color.org), `FORCE_COLOR`, `TERM=dumb`.

Проект определяется подъёмом от текущей директории: первая с `.jarvis/project.yaml`, иначе первая с
`.git`. Переменные окружения: `JARVIS_HOME` (вместо `~/.jarvis`), `JARVIS_CONFIG`, `JARVIS_PROFILE`,
`JARVIS_ACTOR`, `JARVIS_KEYCHAIN_BACKEND`; переменные этого справочника (`JARVIS_LOG`, `JARVIS_LOG_DIR`,
`JARVIS_PROGRESS`, `JARVIS_EDITOR`, `JARVIS_NOTIFY` и др.) — свои; остальные `JARVIS_*` — переопределения
конфигурации (см. [configuration.md](configuration.md#переменные-окружения)).

Идентификатор run принимается полностью (`run_…`) или уникальным префиксом (`e9d5e181`).

## Установка и диагностика

### `jarvis init [--user-only | --project-only]`

Создаёт `~/.jarvis` (config.yaml с шаблоном, базу, каталоги) и `.jarvis/` в проекте (project.yaml,
knowledge/, standards/, skills/ с README, записи в `.gitignore`). Существующие файлы не перезаписывает.

### `jarvis onboard [--dry-run] [--refresh] [--apply-config] [--no-graph] [--module <path> [--note <текст>]]`

Быстрая инициализация знания о существующем репозитории — без модели, детерминированный скан
(нужен git-репозиторий). Что делает:

- строит граф проекта и собирает факты: стеки и менеджер пакетов, модули (файлы, строки, зависимости
  и «кто использует» — из графа), точки входа, найденная документация (README, ADR, CONTRIBUTING, docs/),
  линтеры, CI, тестовые фреймворки и раскладка тестов, стиль коммитов (conventional / тикет-префикс,
  частые scope), часто меняемые файлы, пути, похожие на секреты;
- предлагает команды для `tools.local` (`tests`, `typecheck`, `lint`, `build`) из `package.json` и
  признаков dotnet/go/cargo/maven/gradle/pytest/ruff — с указанием источника каждой;
- пишет `.jarvis/knowledge/architecture.md` и `conventions.md` — короткие фактические заготовки с маркером
  `<!-- jarvis:onboard … -->`. Файл, которого нет, создаётся; существующий не трогается. `--refresh`
  перегенерирует только файлы, где маркер ещё на месте (отредактированные человеком остаются:
  `kept (edited by a human)`).

`--apply-config` заполняет пустой `tools.local: {}` свежего `project.yaml` (заполненный не меняется),
`--dry-run` ничего не пишет, `--json` печатает полный отчёт. Описание того, зачем нужен каждый модуль,
остаётся за человеком или за агентным режимом (ниже).

**Агентный режим (прототип): `jarvis onboard --module <path>`.** Агент `onboard-mapper` (workflow
`onboard-module`, роль `research`, только чтение) читает один модуль — или каталог внутри модуля: в монорепо
модуль — это целый пакет, и `--module packages/lib/src/billing` сужает проход (зависимости тогда названы на той
же глубине внутри пакета и пакетами снаружи) — и описывает: назначение, публичный API,
обязанности, правила, которые легко нарушить, словарь терминов с символами кода и то, что установить не
удалось. Каждое утверждение обязано нести evidence — файл и дословную цитату. Модель себя не проверяет:
детерминированный проход сверяет цитаты с файлами (пробелы нормализуются, строка исправляется на
настоящую), символы API и терминов — с кодом, и отбрасывает всё, что не подтвердилось, а также пути вне
репозитория и под `security.deniedPaths`. Эта сверка — шаг `verify` самого прогона (детерминированный, без
модели), а не команды, которая его начала: прогон, запущенный со страницы `jarvis ui`, остановленный на бюджете и
продолженный позже, всё равно доходит до кандидата. Если не выжило ничего, кандидат не создаётся, шаг `verify`
падает и команда завершается ошибкой. `--note "<текст>"` (до 2000 символов, только с `--module`) добавляет в задачу агента, что важно спросившему
(«как называются события и где каталог»); кандидат хранит заметку и список отброшенного с причинами. Утверждение-обобщение («каждый…», «единственное место…», «нет…»), которое цитата доказать не
может, остаётся, но помечается в документе и выводится списком «check before promoting»: проверка цитат не
доказывает «каждый» — в пилоте так прошло правило команды, которое код соблюдал в трети файлов.
Выжившее становится `candidate` (kind `knowledge`) с `paths: ["<module>/**"]`:
агент ничего не пишет в проект. `jarvis candidates promote <имя>` кладёт готовый документ
в `.jarvis/knowledge/module-<имя>.md` (с `source:` в front matter), и дальше он подаётся агентам только в задачах,
затрагивающих этот модуль. Если файл уже есть: сгенерированный jarvis (маркер `jarvis:onboard…` на месте) заменяется,
написанный человеком — только с `--replace` (или `--id <id>` — другой файл). `--dry-run` показывает задачу агента,
не вызывая модель. То же со страницы — **Knowledge → Modules** в `jarvis ui` (ниже).

### `jarvis logs [run] [--level error|info|debug] [--event <text>] [--tail n] [--since <age>] [--full] [--path] [-f]`

Читает технический лог ([workflows.md](workflows.md#технический-лог)). `run` — полный идентификатор или префикс;
`--level` — самый подробный уровень записей (`info` по умолчанию, `debug` показывает тела запросов и ответов,
если лог писался с `JARVIS_LOG=debug`); `--event` — подстрока имени события (`model.error`, `tool.result`);
`--since 30m|2h|1d`; `--tail n` (100) — последние n записей; `--full` не сокращает длинные значения; `--path`
печатает каталог; `-f`/`--follow` после последних записей печатает новые по мере записи, как `tail -f`. `--json` выдаёт записи как есть. Конфигурацию команда не
загружает: лог нужнее всего, когда конфигурация сломана.

Типовые разборы: `jarvis logs <run> --level error` — почему run упал; `JARVIS_LOG=debug jarvis work …`, затем
`jarvis logs <run> --level debug --event model.` — что получила модель и что ответила; `--event tool.result` — что
вернули инструменты.

### `jarvis doctor`

Один список всего, что мешает старту (в том числе уровень и каталог технического лога): версия Node, конфигурация с источниками значений и ошибками схемы,
версия схемы БД и ожидающие миграции, ссылки на секреты (есть ли значение), сводка политики egress
(ADR-0016), состояние MCP-серверов (discovery, credentials, неизвестные профили), расхождения между
конфигурацией моделей и результатами `models probe`.

### `jarvis errors [code]`

Коды ошибок Jarvis (`J001` …): без аргумента — список, с кодом — что значит и что делать.

### `jarvis config show [--sources]`

Итоговая конфигурация после слияния всех слоёв; `--sources` печатает, откуда взято каждое значение
(cli / env / project / user / profile / default) — ADR-0014 §2.

### `jarvis db status | migrate | backup`

Версия схемы и ожидающие миграции; применение миграций (всегда с бэкапом рядом с базой:
`~/.jarvis/jarvis.db.bak-<версия>`, хранится один последний);
бэкап вручную. Миграции только вперёд (ADR-0014 §4); при открытии БД более новой версии команды
отказываются работать.

## Модели и credentials

### `jarvis models list`

Модели с egress, ролями, пулами квот, использованием текущего окна (и безлимитными часами пула: `unlimited
until …` / `unlimited from …`) и состоянием проб.

### `jarvis models probe <modelId>`

Канареечные запросы: поддерживает ли модель tools, parallel tools, json mode, json schema, system role,
reasoning, prefix cache. Результат записывается и сравнивается с `supports:` конфигурации — расхождения
показывает `doctor` (ADR-0007).

### `jarvis models stats [modelId] [--since <age>]`

Как ведут себя модели за окно (по умолчанию 24h; `30m`, `2h`, `7d`) — из журнала событий (`model.call`,
`model.retry`, `model.error`), без запросов к модели:

```
deepseek-flash  last 24h · 32 answered, 0 failed (100%) · 2 retries
  latency    p50 41s · p90 2m 05s · max 4m 58s   timeout 10m 00s
  speed      p50 38 tok/s · p90 61 tok/s · max 95 tok/s
  streamed   32 of 32 · first token p50 6s · p90 24s · max 1m 02s
  prompt     avg 33k · max 152k · total 1.0M · cached 0% · reusable p50 91%
  output     avg 780 · max 3.2k · total 25k
  finish     tool_calls 24 · stop 8
  failures
    ⚠ network error · UND_ERR_HEADERS_TIMEOUT  2 retried  every attempt ran 5m 01s — a cut-off, not the model  last 10-06 07:10
  by agent   research      22 calls · p50 25s · prompt avg 38k
             requirements   7 calls · p50 1m 12s · prompt avg 21k
```

Отвеченные и сорвавшиеся (после всех повторов) запросы и доля успеха; задержка ответа (p50/p90/max) рядом с
`timeoutMs` модели; скорость — выходные токены в секунду ответа; токены запроса и ответа, доля из кэша
(`cached`, если шлюз о нём сообщает) и `reusable` — сколько промпта повторяет предыдущий вызов шага с начала,
то есть сколько мог бы взять кэш префикса; ответы потоком и время до первого токена;
`finishReason` (`length` — ответ обрезан на `maxOutput`); причины сбоев — причина, HTTP-статус, низкоуровневый
код, сколько повторено и сколько сдалось, сколько шли неудачные попытки. Одинаковая длительность у всех
попыток помечается как обрыв по времени (клиент или шлюз), а не проблема модели. `--json` — всё структурой.

### `jarvis auth set <id> | status | remove <id>`

Credential для ссылки `keychain:<id>` под текущим актором: ввод без эха или через stdin
(`echo $TOKEN | jarvis auth set corp-llm`). `status` показывает только наличие. Бэкенды: macOS Keychain,
libsecret, Windows DPAPI, файл `0600` (fallback; `JARVIS_KEYCHAIN_BACKEND=file|macos|libsecret|windows`).

## MCP

### `jarvis mcp list [--refresh]`

Серверы из `mcp.servers` и их состояние: discovered / exposed / denied / unmapped / «discovered, not
allowed». `--refresh` переподключается к каждому и обновляет кэш `~/.jarvis/cache/mcp/<server>.json`.

### `jarvis mcp call <capability> [--arg key=value]… [--full] [--out <file>]`

Одна возможность на чтение (`jira.get`, `jira.search`, `confluence.get`, `confluence.search`, `bitbucket.pr.*`)
так, как её вызвал бы агент: тот же сервер по профилю, токены, преобразование аргументов, проверки `allow` /
`deny` и сети по `dataClass` (запрет — с той же причиной, выход 12), тот же редактор секретов. Без прогона и
модели; эффекты (`jira.comment`, `confluence.create`, …) не вызываются — только из прогона, с журналом. В stderr —
шапка: сервер, выбранный инструмент, ушедшие аргументы, время, размер; в stdout — только ответ (для `grep` и
файлов), обрезанный, как его видит агент (`tools.maxOutputBytes`), `--full` — целиком, `--out` — в файл.
`--arg` повторяется; `true`/`false` становятся булевыми, остальное — текст. `--json` — всё структурой.

```
jarvis mcp call jira.get --arg key=ABC-123
jarvis mcp call confluence.search --arg query="маска телефона"
jarvis mcp call confluence.get --arg id=123456 --arg raw=true --full | grep -io 'https://[^"<]*figma[^"<]*'
```

### `jarvis mcp serve`

Jarvis как MCP-сервер на stdio (только чтение) для IDE и других агентов: `knowledge.search`,
`spec.get`, `run.status`, `context.inspect`. См. [integrations.md](integrations.md#ide-и-другие-агенты-jarvis-mcp-serve).

## Запуск и жизнь run

### `jarvis work <task> [--workflow <name>] [--base <ref>] [--no-run] [--fresh design]`

Preflight (все MCP-серверы, до которых могут дотянуться агенты workflow, должны ответить на
`tools/list`), создание run, рабочая копия по `workspace.mode`: worktree от `--base` (по умолчанию `HEAD`) или
ваша копия (`cwd`; тогда `diff`/`apply` не нужны), исполнение в foreground до
завершения или остановки. Коды выхода — [overview.md](overview.md#коды-выхода). Workflow по умолчанию
`sdd`; `smoke` проверяет сам движок.

### `jarvis fix <task> [--base <ref>] [--fresh design]`

Короткий путь для бага (встроенный workflow `fix`): `discover → sources → research → spec → approve-spec →
implementation → verify (standards, checks) → review → approve-impl`. Без анализа требований, impact, плана,
документации, телеметрии и release notes — для однострочного исправления `sdd` запускал одиннадцать агентов,
которые перечитывали одни и те же файлы. Implementation без плана реализует требования spec и пишет тесты,
которых требуют её критерии приёмки. `verify` — без модели: стандарты и проверки проекта (`project.checks`):
команды `tools.local` с именами `test*`/`typecheck*`, в пакете которых (`cd <dir> && …`) есть изменённый код;
jest — только связанные тесты (`--findRelatedTests`, с `--passWithNoTests`: нет связанных тестов — не провал). Упавшая проверка — возврат в implementation с командой и
хвостом вывода. Для фич — `jarvis work` (`sdd`).

### `jarvis research <task> [--base <ref>] [--fresh design]` / `jarvis spec <task> [--base <ref>] [--fresh design]`

Частичные прогоны: `research` выполняет только `discover → sources → research`; `spec` — исследование, анализ
требований и спецификацию до её утверждения (выход 10 на гейте; `jarvis approve <run> --resume` завершает run).
Это встроенные workflow `research` и `spec`; их можно заменить файлами `.jarvis/workflows/research.yaml` и
`spec.yaml`. Остальное — как у `work`.

Шаг `sources` модель не вызывает: читает задачу из Jira по ключу (`ABC-123`) и связанные страницы Confluence и
пишет артефакт `sources`; с `contracts` в конфиге проекта сверяет упомянутые методы API (`GET /path`) с картой и
дописывает итог туда же, как и места в коде, где встречаются имена и тексты интерфейса из источников; если доступен `figma.get` — описывает макеты в артефакте `design`. Агенты research и
requirements получают оба на вход и задачу со страницами заново не читают.

Макеты Jarvis хранит сутки (см. [integrations.md](integrations.md)): если дизайн поменяли по той же ссылке, следующая
задача в течение суток получит старый. `--fresh design` (у `work`, `fix`, `spec`, `research`; в UI — галочка «Read
the Figma frames again» в New task) читает все фреймы задачи из Figma заново, мимо кэша, и кладёт новые версии в
кэш — следующие задачи получат уже их. Флаг хранится в run: resume и повтор шага тоже читают заново. Каждый фрейм —
запрос к Figma API; строка шага `sources` и `design.md` пишут «read again from Figma, past the cache».

Противоречия в требованиях research не разрешает молча, а выносит отдельным списком `contradictions`. Это два
источника, которые спорят, одно правило, дающее разным веткам одно и то же условие, текст против макета. Код, который
отличается от требования, — это то, что надо поменять, а не противоречие; противоречием он становится, только если
показывает, что требование в таком виде невыполнимо. У каждого противоречия: обе стороны, источники и один вопрос аналитику. В документе они идут первыми
(`## ⚠ Contradictions`), строка шага говорит `⚠ 2 contradictions in the requirements` — в терминале и на странице
прогона. Агент requirements каждое из них либо закрывает источником, либо считает блокирующим.

Research различает, чьи требования. Свои — то, что делает этот репозиторий. Требования других систем (сервисы других
команд, их API) — это контракт, который репозиторий потребляет: они идут в список `dependencies` (система, что
нужно — метод, поле, формат, — есть ли уже вызов, источник), а не в работу. Противоречие внутри чужой спеки попадает
в список, только если меняет то, что получает репозиторий; поле `owner` говорит, кому вопрос — своему аналитику или
команде той системы. Где проходит граница, агент берёт из знаний проекта: стоит описать её документом в
`.jarvis/knowledge/` (что в репозитории, какие сервисы снаружи и чьи они).

### Терминал: что видно по ходу прогона

Принципы — [ADR-0022](adr/0022-terminal-interface.md). Всё ниже — только в терминале: в pipe, CI и `--json`
ничего не перерисовывается и не пишется управляющих последовательностей.

- **Строки, которые остаются.** Заголовок прогона с планом, строка на каждый завершённый шаг (`[k/N]`, время,
  агент, вызовы, токены, инструменты — `read×12 search×4 edit×2 (18/40)`), возвраты по рёбрам, остановки.
  Ошибки — с кодом и подсказкой: `error[J002]: …` и строка `help: …`; `jarvis errors` — список кодов,
  `jarvis errors J002` — подробно.
- **Живая область** внизу, одна или две строки: где прогон и чего ждёт (`waiting 1:24, thinking ~3k tok`), под
  ней — последние вызовы инструментов шага (`↳ read src/a.ts · search foo`). Перерисовывается одним кадром
  (synchronized output, DEC 2026) и всегда помещается в ширину окна, в том числе после его изменения.
- **Вкладка.** Заголовок: `▶ jarvis 6/14 implementation`, `⏸ jarvis needs you at approve-spec`,
  `⏸ jarvis waits for the model`, `✓ jarvis done`, `✗ jarvis failed`. Прогресс во вкладке или на панели
  задач (OSC 9;4): доля пройденных шагов, «внимание» на остановке, «ошибка» при падении — в Windows Terminal,
  ConEmu, Ghostty и iTerm2 3.6+.
- **Уведомление**, когда прогон дольше 30 с остановился ради человека, закончился или упал: OSC 9 в iTerm2,
  WezTerm и Ghostty, звонок в остальных; внутри tmux — при `set -g allow-passthrough on`.
- **Ссылки** (OSC 8): артефакты в строках шагов, итоге и `jarvis show` открываются кликом — документы агентов
  как markdown из `~/.jarvis/cache/view/<run>/`.
- **Метки** (OSC 133) перед каждой строкой шага и остановкой: клавиша терминала «к предыдущей метке»
  листает длинный прогон по шагам (iTerm2, WezTerm, Ghostty, kitty, VS Code, Windows Terminal; не в tmux).
- **Ctrl-C** в две ступени. Первое: текущий вызов модели отменяется, разговор агента сохраняется, прогон
  паркуется (`SUSPENDED`, выход 130), и `jarvis continue` продолжает с того же места. Второе: выход сразу.

`--progress auto|tty|plain|json` (или `JARVIS_PROGRESS`): `auto` — перерисовка в терминале, строки в остальном;
`tty` — перерисовка всегда (запись экрана); `plain` — только строки и через полминуты тишины строка-пульс
(`… 3:20 · spec#1 specification · model call 2, waiting 1:40`) — в логе CI видно медленный вызов, а не
зависание; `json` — события прогона JSON-строками в stderr, ничего для людей (итог `--json` — в stdout).

| Переменная | Что |
|---|---|
| `JARVIS_PROGRESS` | как `--progress`; `off` — то же, что `plain` |
| `JARVIS_NOTIFY` | `auto` \| `osc9` \| `osc777` \| `bel` \| `off` |
| `JARVIS_NOTIFY_AFTER` | секунды, после которых прогон стоит уведомления (30) |
| `JARVIS_TITLE` | `off` — не трогать заголовок вкладки |
| `JARVIS_TAB_PROGRESS` | `on`/`off` — прогресс во вкладке вопреки определению терминала |
| `FORCE_HYPERLINK` | `1`/`0` — ссылки вопреки определению терминала |
| `JARVIS_MARKS` | `on`/`off` — метки OSC 133 |
| `JARVIS_PAGER` | `off` — документ на гейте печатается, а не открывается в `$PAGER` |
| `JARVIS_ACCESSIBLE` | `1` — доступный режим: ничего не перерисовывается, строки начинаются со слова (`done:`, `failed:`, `waiting:`), меню гейта нумерованное, на гейте звонок |
| `JARVIS_ASCII` | `1` — ASCII вместо значков (`v`, `x`, `||`, `->`); само включается в консоли Linux и при локали не UTF-8 |
| `NO_COLOR`, `FORCE_COLOR`, `--color`, `--no-color` | цвет |

### Решения по ходу прогона и `jarvis continue [run]` (`jarvis c`)

Когда `work`, `spec`, `research`, `resume`, `approve --resume` или `continue` в терминале доходят до
человека, команда не выходит, а спрашивает на месте и идёт дальше в том же процессе:

```
⏸ [5/5] approve-spec  waiting for approval — approve spec (spec.json@1)

  Баг: в компактном режиме показываются поля доставки
  Причина: order-form.tsx:89 — условие не учитывает isCompact
  5 requirements · 3 risks · 3 open questions
  risk Компактная форма оформления заказа может опираться на этот блок
  whole: spec/spec.json@1

  enter read it whole    a accept    c send back with changes    e …in $EDITOR    q decide later    ? help
> c
  answer the open questions (empty line skips one):
  1/3 Должны ли поля доставки показываться в компактном режиме хоть когда-нибудь?
  > нет, никогда
  …
  what else to change? (empty line sends)
  >
↻ sent back spec/spec.json@1 with your changes
```

Карточка — сначала итог: заголовок, суть, что в документе, первые риски, для реализации — изменённые файлы
(`+12 −3 path`, больше всего изменённые сверху) и ссылка на документ целиком. `enter` — документ целиком в
`$PAGER` (`less` с `LESS=FRX`, как git; где пейджера нет — печатается), `a` — принять, `c` — вернуть:
открытые вопросы документа задаются по одному, ответы и всё, что дописано после, становятся комментарием к
возврату (`request_changes`), `e` — то же в `$VISUAL`/`$EDITOR` по шаблону с вопросами (строки с `#`
отбрасываются, пустой файл ничего не отправляет), `q` — оставить ждать, `?` — что делает каждая клавиша.
Enter никогда не принимает. Уточняющие вопросы агента (`waitingFor: clarification`) идут тем же мини-чатом, что
`jarvis attach`. Спрашивает только человека у терминала: stdin и stdout — TTY, не `--json`,
`interactive: true` (профиль `ci` выключает); `JARVIS_INTERACTIVE=off` отключает, `on` включает
принудительно. Иначе — как раньше: выход 10 и команды в итоге.

Исчерпанная петля (`waitingFor: loop`: ребро вроде `verify → implementation` вернуло работу `maxIterations`
раз) — карточка: причины последнего круга по одной в строке (вид причины колонкой, обрезка по ширине окна) и
рабочая копия прогона (`~/…`, открывается кликом). `o` — открыть рабочую копию в редакторе (см. ниже); карточка
остаётся на месте и **следит за рабочей копией**: что ты изменил в редакторе, появляется строкой `changed` само.
`r` — запустить шаг заново (новым кругом, с ручной правкой как checkpoint), `enter` — причины целиком, `q` —
позже. `s` — запасной путь, шелл в рабочей копии: правишь и набираешь привычное `jarvis c` — карточка сама
закрывает шелл и идёт дальше; `exit` (Ctrl-D) — назад на карточку. Тот же повтор — `jarvis resume <run>`.
Снова дефекты — снова эта карточка.

```
⏸ verify sent the work back 2 times — verify → implementation, defects_found; no rounds left
  • lint_error   project.lint: eol-last в новом тестовом файле…
  • stray_files  tmp-eol-test.txt в корне рабочей копии…

  fix it by hand in the run's checkout  ~/.jarvis/worktrees/web-app/1a2b3c4d-compact-form

  enter reasons    o open in your editor    s a shell there    r run verify again    q later
> o
  ↗ opened in VS Code · this card watches the checkout — save there, then r here
  changed  D tmp-eol-test.txt  M …/upload-toggle.test.tsx  · r runs verify again with them
>
```

Остановка на бюджете (`waitingFor: budget`): лимит `budget.perStep|perRun` или, у шага с `onLimit: ask`,
лимит вызовов агента — карточка: что кончилось и откуда лимит, что уже изменено в рабочей копии. `enter` —
добавить половину лимита и продолжить с того же места (разговор агента сохранён), `m` — другое число, `f` —
закончить шаг с тем, что есть (результат помечается неполным), `q` — позже. То же — кнопками на странице
прогона в `jarvis ui`; решение со страницы карточка подхватывает сама, а если карточки нет — прогон продолжает
страница. В безлимитные часы пула лимиты агентов и `budget.perStep|perRun` умножаются на
`quotaPools.<pool>.unlimitedScale` (по умолчанию 10).

```
⏸ implementation stopped: 80 of 80 tool calls — the implementation agent's limit (agents.implementation.limits)
  its conversation is kept: more calls go on from where it stopped
  changed  M src/upload/List.tsx  A src/upload/List.test.tsx

  enter +40 tool calls and go on    m another amount    f finish with what it has (marked incomplete)    q later
```

На гейте прогона с собственной рабочей копией (worktree) в меню есть и `o` — открыть изменения в редакторе,
прежде чем принять или вернуть.

Карточка следит и за прогоном (раз в секунду, по журналу событий): решение, принятое в другом месте, она
подхватывает сама — `jarvis approve` из другой вкладки или кнопка на странице `jarvis ui`. Тогда вместо
ответа на вопрос появляется строка `✓ accepted in the browser by dev@example.com` (`↻ sent back …`,
`✗ rejected …`; «Run verify again» со страницы — `↻ verify runs again (asked in the browser by …)`), и
команда идёт дальше, как после своей клавиши. Если прогон тем временем продолжил другой процесс
(`jarvis approve --resume`, `jarvis resume`), терминал не перехватывает его аренду, а следит за ним, как
`jarvis follow`, и снова показывает карточку, если прогон остановится ради человека. Решение, принятое
раньше, чем открылась карточка (`jarvis approve` без `--resume`, затем `jarvis c`), не спрашивается второй
раз: `✓ accepted in the terminal by …` — и прогон идёт дальше. По одной версии артефакта — одно решение:
второе (`jarvis approve` по уже решённой версии) отвергается — `spec/spec.md@1 is already decided: approve
by … at …` ([ADR-0023](adr/0023-editor-and-web-ui.md) §4).

`jarvis continue` без аргументов находит прогон этого репозитория, который ждёт: решения человека, окна квоты
или прерван (остановлен Ctrl-C — `SUSPENDED`, или RUNNING без процесса — закрытый терминал); несколько —
список на выбор, — и открывает тот же диалог; с id — этот прогон. Прогон, остановленный на квоте, упавший
или прерванный, продолжается как `resume`. `approve`, `answer` и флаги остаются для скриптов и CI.

Модель недоступна. Когда шлюз отказал после своих повторов (сетевая ошибка, 5xx, таймаут), прогон не падает,
а ждёт модель (`WAITING_BUDGET`, `waitingFor: model`, в статусе — «waits for: the model»). В терминале команда
ждёт на месте: обратный отсчёт до проверки, одна короткая попытка (`noRetry`), и прогон идёт дальше, когда
модель ответила; Ctrl-C оставляет его ждать.

```
⏸ model deepseek-flash is unavailable since 18:02 (provider error (500)) — waiting here; Ctrl-C leaves the run parked
check 2: still unavailable (network error)
✓ model deepseek-flash answers again (0:12) — going on
```

`jarvis continue` для такого прогона сначала проверяет модель и только потом тратит на неё настоящий запрос;
демон (`jarvis daemon`) продолжает его после `resumeAfter`. Проверка — раз в `modelWait.checkEveryMinutes`
(5), прогон падает как раньше, если модель недоступна дольше `modelWait.giveUpAfterHours` (12) —
[configuration.md](configuration.md).

Одобренная spec идёт дальше. Когда `spec` (или `research`) завершился в терминале, Jarvis спрашивает «Go on
to the implementation? impact → plan → implementation → …» и по `Y` (Enter) продолжает той же командой: новый
прогон `sdd` начинается после одобрения spec — research, requirements и spec (с их одобрением) переносятся
в него, ничего не повторяется. Workflow объявляет, куда может продолжиться, полем `next:` (у `spec` и
`research` — `sdd`). Прогон `sdd` работает в своём worktree (`workspace.mode: worktree`, с `workspace.setup`),
ваша копия не меняется до `jarvis apply`. Без терминала итог подсказывает `jarvis continue <run>`;
`jarvis continue` без id находит одобренные за последние три дня spec, которые ещё не продолжены.
В `jarvis ui` то же делают кнопка **Continue to sdd** на странице завершённого прогона и галочка «Start from the
research…» в New task (см. ниже).

### `jarvis resume <run> [--steal]`

Продолжить парковавшийся, упавший или оборванный run с последнего checkpoint: транскрипт агента
восстанавливается, worktree приводится к checkpoint-коммиту (ручные правки в нём становятся
checkpoint `human edit`, см. [human.md](human.md#ручные-правки-в-worktree)). `--steal` забирает аренду у
процесса, который перестал слать heartbeat.

### `jarvis status [run] [--all] [--watch N] [--events n]`

Без аргумента — активные run и бюджеты пулов, сверху те, что ждут человека, затем остановленные (прерванные,
упавшие), ждущие квоты, идущие; `--all` добавляет завершённые. С run — состояние, что
ждёт (`waitingFor`), уровень возможностей проекта, шаги с итерациями и исходами, checkpoint, артефакты
и утверждения, эффекты, события, токены. `--watch N` обновляет каждые N секунд и сам останавливается
(со звуковым сигналом), когда run завершился или ждёт человека.

Пока run исполняется, строка `now` говорит, что он делает сейчас, — та же, что рисуют команды прогона (`work`,
`fix`, `spec`, `research`, `resume`, `continue`, `approve --resume`), `onboard --module` и `ask` в терминале
(stderr, раз в секунду):

```
⠼ 6:12 · map#1 onboard-mapper · model call 8, avg 0:42, waiting 1:24 · tools 21/40 [█████░░░░░] · tokens in 98k out 4.1k/60k · last repo.read …/senders/invoice-mailer.ts
```

Прошло с начала, шаг и агент, вызовы модели и сколько ждём текущий ответ (дольше трёх средних — «slower than
usual», дольше `timeoutMs` модели — «past the model timeout»), расход бюджета инструментов шага, токены (с
лимитом `budget.perStep`), последний инструмент. Оставшегося времени нет сознательно: агент сам решает, когда
закончил; шкала показывает израсходованный бюджет инструментов, который шаг ограничивает. Строка строится из
журнала событий, поэтому `status --watch` из другого терминала видит то же. Не рисуется в `--json`, в pipe и
при `JARVIS_PROGRESS=off`.

Над строкой прогресса остаются сообщения, которые разработчику нужно видеть без лога (в stderr; в pipe и с
`--json` тоже): каждый повтор вызова модели — причина, сколько шла неудачная попытка, номер повтора из
допустимых, пауза и `traceId` провайдера; окончательный отказ модели; переход вызовов на следующую модель роли
(`↪ 13:40:02 a → b: the quota window of pool X is full — calls go to b until it frees`: пул первой модели полон,
у роли есть модель в другом пуле со свободным окном — без паузы); run `FAILED` или `WAITING_BUDGET`.

```
⚠ 13:22:22 deepseek-flash: provider error (500) after 5:00 — retry 1/2 in 0.5s; traceId 0f1e2d3c4b5a69788796a5b4c3d2e1f0
✗ 13:32:23 deepseek-flash: provider error (500) after 5:00 — gave up after 3 attempts
```

Одинаковое `after 5:00` у всех попыток — признак того, что запрос обрывает шлюз, а не модель.

Сжатие разговора видно отдельно. Пока пишется сводка (это свой вызов модели, до минуты), живая строка говорит
`compacting the conversation (57k tok, 6 blocks into a summary), waiting 0:32` вместо `model call N`; то же — на
странице прогона в `jarvis ui`. Итог остаётся строкой и в ленте:

```
⇣ 14:02:11 conversation compacted: 57k → 48k tok, 6 blocks into a summary
```

Если сводка пришла пустой или обрезанной, строка говорит и это.

Ход прогона. `work`, `spec`, `research`, `resume` и `approve --resume` печатают в stderr шапку (workflow,
задача, короткий id run и план шагов), а каждый завершённый шаг оставляет строку-отчёт — под ней дальше
рисуется живая строка следующего шага. Остановка на человеке или квоте и падение — тоже строкой:

```
▶ spec · ABC-1 · run 1a2b3c4d
  discover → sources → research → requirements → spec → approve-spec
✓ [1/6] discover      0.4s    deterministic  → project-capabilities.json
✓ [2/6] design        2.1s    deterministic  → sources.md, design.md
✓ [3/6] research      3m 12s  research · 9 calls · 182k→6.1k tok · 23/60 tools  → research.md
✗ [4/6] requirements  1m 02s  requirements · 4 calls · 61k→2.0k tok · 12/60 tools
  error: …
↻ approve-spec → spec request_changes, round 1/3 — слишком общо
⏸ [5/5] approve-spec  waiting for approval — approve spec (spec.md@1)
```

Позиция `[k/N]` — место шага в workflow (`#2` — повторный проход), время шага, агент, вызовы модели,
токены (вход→выход), инструменты из лимита («tool limit reached», если упёрся), повторы, исход, отличный
от успеха, и `→` артефакты, которые шаг создал. Строки идут и в pipe, и с `--json` (stdout остаётся JSON).
В конце в stdout — итог: состояние, время в шагах, модель, артефакты с отметкой утверждения и `next` —
команды для следующего шага (прочитать артефакт, утвердить или вернуть с замечаниями, `diff`/`apply`,
`logs` при падении, `status` для подробностей).

### `jarvis forget <run…> | --all [--yes]`

Законченные прогоны (COMPLETED, CANCELLED, FAILED) уходят из хранилища Jarvis: запись, история шагов,
checkpoints, события, артефакты (и документы, на которые больше никто не ссылается), одобрения, треды,
файлы для чтения, а также рабочая копия и ветка, если `gc` их ещё не убрал. Использование квоты остаётся:
оно принадлежит окну пула. `--all` — все законченные прогоны этого репозитория. Отменить нельзя, поэтому
у терминала спрашивает, без терминала нужен `--yes`. Идущий или ждущий прогон не забывается — сначала
`jarvis cancel`.

### `jarvis open [run]`

Рабочая копия прогона в редакторе — то же, что `o` на карточке, — и сразу файлы для ревью: сначала те, что
названы в причинах (`…/a.test.tsx:113` — на этой строке), затем изменённые прогоном, больше всего изменённые
сверху, каждый на первом изменении; до 8 файлов, без удалённых и пробных. Редактор: `JARVIS_EDITOR`
(команда, можно с аргументами: `idea`, `code -n`), иначе первая найденная команда `code`, `cursor`,
`webstorm`, `idea`, `zed`, `subl` (и скрипты JetBrains Toolbox), на macOS — лаунчер внутри установленного
приложения, иначе файловый менеджер (только папка). Файлы открываются так, как их принимает редактор:
`code <dir> -g a.ts:113`, `webstorm <dir> --line 113 a.ts` (в проекте, а не в LightEdit), `zed <dir> a.ts:113`. Без id — последний
незавершённый прогон этого репозитория. Те же прогоны в браузере — `jarvis ui` (ниже).

### `jarvis ui [--port N] [--open | --no-open]`

Прогоны этой машины на локальной странице ([ADR-0023](adr/0023-editor-and-web-ui.md) §3, §5): читать и
решать в браузере удобнее, чем в пейджере, — дифф по файлам, документ целиком, переходы между артефактами.
Ведёт прогон по-прежнему терминал; страница — ещё одно окно над тем же журналом событий.

- **Runs** (`/`): сверху — что ждёт тебя (исчерпанная петля с причинами, остановка на бюджете, одобрение
  документа с его сутью, исследование модуля, готовое к проверке; у решённого, но стоящего прогона — Resume;
  остальное, например вопросы агента, — с командой для терминала), затем идущие прогоны (текущий шаг, вызов модели, бюджет инструментов полосой), затем
  недавние (состояние, время, вызовы модели): все завершённые прогоны по 10 на страницу («← Newer / Older →»; рядом — 10 / 15 / 20 / 30, выбор
  запоминается в браузере).
  Поиск над ними ищет по мере ввода, по всем полям прогона: id (полный или начало), задача, workflow, состояние и
  его причина, автор, репозиторий, ветка, шаг, дата (`2026-10-07` или `07.10.2026`). Каждое слово должно найтись
  в каком-то поле, фраза в кавычках — целиком; совпадения подсвечены, запрос остаётся в адресе (`?q=`).
  Выбор репозитория — по умолчанию текущий, можно «все».
- **Run** (`/runs/<id>`): состояние, workflow, время в шагах, вызовы модели и токены; шаги по плану
  workflow с последним кругом, вложенными этапами composite (verify) и возвратами петель; карточка решения
  того же вида, что в терминале (причины, рабочая копия с живым списком изменений, кнопка копирования
  пути и команды); лента событий (последние 5 открыты, всё более раннее — свёрнуто над ними, «N earlier»; раскрытое
  остаётся раскрытым при живом обновлении); артефакты.
- **Артефакт** (`/runs/<id>/artifacts/<тип>/<имя>?v=N`): документ (JSON-результат — как в `jarvis show`,
  markdown — как markdown), версии, краткая сводка для решения; для реализации — дифф прогона по файлам
  (`git diff` от базового коммита в рабочей копии) с номерами строк.

Решения на странице — те же, что клавиши карточки, и записываются той же функцией с актором CLI этой машины
(ADR-0006) и `channel: ui`:

- **Accept / Send back** на странице артефакта, которого ждёт прогон. К возврату — комментарий и замечания
  к строкам диффа (кнопка `+` у строки, с клавиатуры — Tab и Enter): они уходят одним комментарием,
  строка на замечание — `путь:строка — текст`, как маркеры Review Mode
  ([human.md](human.md), ADR-0019 §5). Кнопка показывает, сколько замечаний уйдёт: «Send back with 2
  comments».
- **Открытые вопросы документа** (`openQuestions` у спеки, требований) — вкладка **Questions** над документом.
  Перед гейтом Jarvis готовит к ним ответы одним вызовом модели по тому, что прогон уже собрал: задача, её
  страницы и макеты (`sources`, `design`), research, требования, уточнения. На каждый вопрос: **From the
  sources** — ответ с указанием, где он стоит (страница и раздел, ключ задачи, `путь:строка`, узел Figma), выбран
  заранее; противоречие, которое снимают сами источники (таблица важнее примера, целевой макет важнее текущего), —
  тоже ответ; **The sources don't settle it — your call** — 2–3 варианта с последствиями и источниками; предложен
  вариант, на который указывают задача и целевой макет, а текущее поведение — только там, где задача его не меняет; **Only
  someone else can say** — аналитик, юристы, другая команда. Источник проверяется кодом: ссылка должна называть
  то, что есть в материале прогона или в рабочей копии; ответ без такой ссылки показан как «Jarvis's guess» и не
  выбран. Для каждого вопроса ещё **My answer** (свой текст), **Ask the analyst** (вопрос остаётся открытым, в
  рисках) и **Not in scope**. **Send back with the answers** собирает ответы в начало комментария («Answers to
  the open questions (binding for the next version)»), заметка («+ A note» под вопросами) и замечания к строкам идут следом; ответы
  сохраняются артефактом `answers` рядом с версией и видны на ней потом. Пока вопросы открыты, правой колонки нет:
вопросы, решение под ними и документ — на всю ширину; у документа без вопросов колонка с кратким содержанием и
кнопками остаётся. Гейт, до которого ответы не готовили
  (прогон старше этой версии или модель не ответила), готовит их при открытии страницы — около минуты, страница
  обновится сама. Выключить — `human.suggestAnswers: false`.
- На карточке исчерпанной петли: **One more round of implementation** — ещё один круг шага, куда вело ребро
  (implementation получает причины последнего круга и твои заметки, потом снова verify); **Run verify again**
  (как `r`) — только verify, когда ты сам поправил рабочую копию; **Open in editor** (как `o`: рабочая копия
  в редакторе, сначала файлы из причин, на их строках); **✎ Add a note for implementation** — заметка, которую
  агент получит как обязательную. Порядок: заметка, потом «One more round». Если ребро ведёт в тот же шаг —
  только Run again.
- На гейте реализации — **Try it before you decide**: на странице прогона одна строка `cd <рабочая копия> &&
  <запуск>` с Copy; на странице реализации (вкладка **Try it**) — шаги: перейти в рабочую копию, запустить
  (`workspace.try.run`, иначе догадка по package.json), проверить руками критерии приёмки из спеки, **Open in
  editor**, `git diff` диапазона, вариант в основном репозитории и что сделают Accept / Send back. Своя правка
  в рабочей копии уйдёт как `human edit`. Настройка — `workspace.try` ([configuration.md](configuration.md)).

В шапке — **индикатор моделей**: точка и `models`. Зелёная — модели отвечают; жёлтая — нагрузка: окно
квоты пула выше мягкого порога (`soft`), прогоны ждут окна квоты, частые повторы или больше 10% отказов за
полчаса; красная — модель недоступна (сдалась после повторов и с тех пор не отвечала, прогоны ждут её) или
окно квоты исчерпано; серая — вызовов не было. По клику (не по наведению: так работает и на телефоне, и с
клавиатуры, а содержимое можно читать и выделять) — поповер по каждой модели: состояние и почему, окно
квоты полосой (входные и выходные токены и запросы из лимита), вызовы, отказы, повторы и p50 задержки за 30 минут,
последний отказ, ждущие прогоны со ссылками; внизу — «At once»: сколько запросов к моделям идёт сейчас по всем
прогонам и процессам (какие прогоны ждут ответа) и пик за сегодня с временем. Esc или клик мимо закрывает; при наведении — подсказка одной
строкой. Обновляется раз в 10 с и после каждого события журнала. Подробнее в терминале — `jarvis models
stats` и `jarvis models list`.

Пока модель не ограничена, на кнопке рядом с `models` горит зелёная метка:
- `∞ until 07:00` (`∞ until Mon 07:00`) — идут безлимитные часы её пула (`quotaPools.<pool>.unlimited`);
- просто `∞` — у пула модели нет лимитов совсем (например, отдельный кластер).

В поповере у такой модели та же отметка, а окно квоты в эти часы не делает её «busy». Вне безлимитных часов там
написано, когда они начнутся (`unlimited hours from 22:00`).

Рядом — **индикатор MCP** (`mcp`), так же точкой и поповером. По каждому серверу из `mcp.servers`:
профиль, сеть, транспорт, команда и ссылки на токены (`keychain:…`, без значений); проверка — ответил ли
сервер (своё подключение, список инструментов, время), когда инструменты обнаружены и сколько их; exposed /
denied / unmapped / «not allowed», как `jarvis mcp list`; за 30 минут — вызовы агентов, отказы, отказы
политики, задержка p50/p90/max, какие возможности вызывались и последний отказ. Красная — сервер не
ответил на проверку, неизвестный профиль или сеть запрещена `dataClass`; жёлтая — профилю не хватает
инструментов сервера, сервер ничего не отдаёт агентам, не обнаружен или были отказы вызовов. Проверка — при
старте `jarvis ui`, раз в 10 минут и кнопкой **Check now** (сервер через `uvx`/`npx` поднимается секунды,
поэтому никогда не в запросе страницы); она же обновляет кэш инструментов, как `jarvis mcp list --refresh`.

**Уведомления** — колокольчик в шапке: по клику браузер один раз спрашивает разрешение (без клика браузеры
не спрашивают; `127.0.0.1` для них безопасный источник). Включённые, они приходят системным уведомлением, когда
прогон начинает ждать тебя (одобрение, исчерпанная петля, бюджет, вопросы агента), а вкладка не в фокусе:
«Jarvis: approve the spec» и задача; клик открывает прогон. Что уже ждало при открытии страницы — на странице,
об этом не уведомляет; прогон, у карточки которого ждёт терминал, оставлен терминалу (он уведомляет сам);
несколько вкладок не дублируют друг друга. Выбор хранится в этом браузере; повторный клик выключает.

Тема по умолчанию — как в системе (`prefers-color-scheme`); переключатель в шапке (луна на светлой, солнце
на тёмной) меняет светлую на тёмную и обратно. Выбор хранится в cookie, поэтому страница сразу рисуется в
нужной теме, без вспышки светлой; выбор, совпавший с системной темой, cookie снимает — снова «как в системе».

**New task** (кнопка в шапке, форма вверху Runs): что сделать, workflow (`research` — разобраться и записать,
ничего не меняя, выбран по умолчанию; `fix` — короткий путь для бага; `sdd` — полный со спекой на одобрение;
`spec`) и репозиторий (тот, где запущен `jarvis ui`, или
любой с прогонами). Галочка «Read the Figma frames again» — то же, что `--fresh design`: макет поменяли по той же
ссылке. Start запускает тот же CLI, что набрал бы человек (`jarvis research "…"`, `jarvis fix "…"`), в фоне и без
терминала, вывод — в `~/.jarvis/cache/launches/`. Пока готовится рабочая копия, запуск виден в Running
со ссылкой на лог; упал до прогона — хвост лога там же. Такой прогон **ведёт страница**: где он ждёт
человека, решаешь на странице, и он идёт дальше сам (`jarvis resume` в фоне); ждал модель или окно квоты —
продолжается, когда ожидание кончилось, пока открыт `jarvis ui`.

**Продолжение research в sdd.** На странице завершённого `research` (или `spec`), который ещё никто не продолжил,
вместо пустой карточки — «Take it into the full cycle»: с какого шага начнёт `sdd`, что переносится (выводы,
противоречия, зависимости) и какие шаги дальше. **Continue to sdd** — то же, что `jarvis continue <run>`, в фоне;
повторный клик, пока готовится рабочая копия, ведёт к тому же запуску. После — отметка «→ continued in sdd» со
ссылкой на новый прогон, а у нового под заголовком «continued from research …». Без лаунчера (`jarvis ui` только
для чтения) карточка подсказывает команду.

В New task, когда выбран workflow, в который продолжаются другие (`sdd`), Jarvis по мере ввода ищет завершённый
и не продолжённый прогон той же задачи в том же репозитории: по ключу (`ABC-42`), а без ключа — по тому же тексту.
Найденный предлагается галочкой «Start from the research of 20:35 — id · N contradictions»; с ней Start запускает
`jarvis continue <run>` вместо нового прогона. Галочка стоит, если код, который research читал (`repo.read`), с тех
пор не менялся: Jarvis смотрит коммиты от базы research до `HEAD` репозитория. Если хоть один прочитанный файл
изменён — «⚠ code changed since: N commits, M files it read among them (…)», и галочка снята: безопаснее новый
research. Без базового коммита Jarvis так и пишет — «can't tell whether the code changed since». Ничего не
нашлось — строка «No finished research of ABC-42 in this repository».

**Пункт плана во время реализации.** Пока идёт `implementation`, в карточке Now — свёрнутая строка «Plan 3 of 7:
описание пункта»; по клику — панель: полоска пунктов (готовые, текущий, впереди), файлы и проверка текущего пункта,
что агент правит сейчас и сколько файлов пункта уже тронуто, весь план списком. Раскрытая панель остаётся раскрытой
при обновлении страницы. Тот же «plan 3 of 7» — у шага в Steps и у прогона в Running. Где агент, Jarvis знает из
двух сигналов: его отметок `plan.step` (start/done по id пункта — инструмент без эффектов, уходит в той же пачке,
что чтения) и, если отметок нет, из записанных файлов: пункт готов, когда тронуты все его файлы. Пункт впереди
незаконченного — пометка «out of plan order».

**Заметка агенту на ходу.** В карточке Now — «✎ Add a note for <шаг>»: текст уходит агенту текущего шага перед его
следующим вызовом модели как обязательный («перекрывает входы, где расходится с ними») и всем шагам после него
(раздел «Notes from a person during the run» во входах). Под формой — заметки рана: «◌ goes with its next model call»
→ «✓ the agent got it». Пилот: дефект оказался ошибкой в спеке, а сказать об этом было некуда до следующего гейта.

**Круг доработки.** Шаг, вернувшийся по обратному ребру (`verify → implementation#defects_found`), вместо плана
показывает свёрнутую строку «Round 2 of 3 · Fixing N defects verify found»; раскрыть — причины от шагов, что вернули.

**Уточнение (clarification)** отвечается на странице прогона, как в `jarvis attach`: карточка показывает вопрос
агента и ход разговора, поле «Your answer» и кнопки. **Send the answer** — ответ сразу ложится в тред, а ход Jarvis
(вызов модели) идёт в фоне: он спрашивает дальше или предлагает правило, страница обновляется сама. Предложенное
правило видно отдельным блоком с поправками к требованиям и допущениями; **Accept the rule and go on** принимает
его. «Write the rule yourself» — своё правило вместо предложенного. После принятия появляется артефакт
`clarification`, и прогон идёт дальше в фоне (`jarvis resume`). Когда ходы закончились
(`human.clarification.maxTurns`), остаются только принять или написать правило. Не ответила модель — в треде
строка с ошибкой, ответ можно отправить снова. В списке Runs у такого прогона карточка «⏸ clarification · шаг» с
вопросом и кнопкой Answer. Если в другом прогоне той же задачи (тот же ключ, тот же репозиторий) уточнение уже
решено, карточка предлагает это правило сверху: «Decided before for this task» и **Accept this rule and go on** —
спрашивать заново не нужно.

**Cancel run…** на странице прогона (красная кнопка справа от заголовка, пока прогон не закончился) — то же, что
`jarvis cancel`: прогон, который сейчас никто не исполняет (ждёт человека, окно квоты, прерван), отменяется сразу;
исполняемый — после текущего вызова модели или инструмента. Клик открывает подтверждение: **Cancel the run**
отменяет, **Keep it**, Esc или клик мимо — закрывают. Рабочая копия и артефакты остаются.

Прогон на паузе (`WAITING_BUDGET`: окно квоты пула заполнено или модель не отвечает) — не ошибка: в Runs он стоит
среди идущих («⏸ waits for the quota window of <pool> · goes on 14:45»), на его странице — карточка «paused, not
failed» с тем, что заполнено в окне, и временем продолжения. Прогон, который ведёт страница, она сама продолжит в
это время, пока открыт `jarvis ui`. **Resume now** пробует сразу (страница начинает вести прогон, если его никто не вёл): окно всё ещё
полное — прогон снова встаёт на паузу. Та же карточка — у исследования на вкладке Modules.

**Knowledge** (пункт в шапке) — база знаний так, как её получают агенты. Вкладки:
- **Overview** — «Would an agent find it?»: тот же поиск, что у агентов (индекс обновляется перед поиском), с
  расширениями глоссария и найденными единицами; таблица документов (о каких путях, в скольких прогонах были в
  контексте, когда правились); «May be stale» — коммиты под `paths` документа после его последней правки,
  сгенерированные и никем не принятые документы, проблемы глоссария; папки, которые стоит исследовать первыми.
- **Ask** — `jarvis ask` на странице. Вопрос; «Sources only» — поиск без модели, сразу: найденные документы с
  кусочком текста и тем, как найдены (по словам, через глоссарий), и термины глоссария из вопроса. «Answer» — тот
  же поиск, затем отдельный ран `ask` в фоне (виден и в Runs): страница следит за ним, ответ приходит с выдержками,
  каждая сверена с текстом источника; что не нашлось в источнике, названо; что знания не покрывают — списком;
  «General knowledge too» разрешает ответ общими знаниями, отдельным помеченным блоком. Без источников и без этой
  галочки модель не вызывается. Справа — последние вопросы и чем кончились.
- **Documents / Architecture** — дерево: архитектура и модули, остальное, `documentation/` (только чтение);
  front matter, текст, как индекс режет документ на единицы, кто его читает и в скольких прогонах он был.
- **Standards** — правило, уровень, как проверяется (шаблон или review), где действует; что нашла
  детерминированная проверка в последних прогонах.
- **Skills** — проектные, из `documentation/` и встроенные; кто кого перекрывает; для каких агентов, задач и
  путей; дошёл ли навык до агента (был в контексте вызова или запрошен по имени через `knowledge.read`).
- **Glossary** — таблица с проблемами (символа нет в коде, синоним у двух терминов), фильтр, у термина — где
  его символы в коде. **Add a term**: термин, синонимы, символы, источник, определение; **Check in the code**
  сверяет символы (имя — словом в коде, путь — папка или файл, `@scope/pkg` — в package.json); не найденный
  символ просит «Add anyway». Строка добавляется в конец таблицы `glossary.md` в её колонках, черновиком.
Документы, стандарты и навыки страница не правит — **Open in editor** открывает файл, **Copy path** копирует
путь. Внизу каждой вкладки — незакоммиченные файлы `.jarvis/…` и **Commit knowledge**.

**Knowledge → Modules**: исследование модуля без терминала. Слева — дерево модулей
скана (`src/<x>`, `packages/<x>`, …) до папок внутри, у каждой — число файлов и что о ней знают: свой документ
(`paths` в front matter), сгенерированный, документ о более широкой папке, документация команды
(`knowledge.sources` со `scopes`), «may be stale» (коммиты в папке после последней правки документа) или ничего;
фильтр **Need research**; поле Path с подсказками по всем папкам. Справа — выбранная папка:
- **Start research** с необязательным «What matters» запускает `jarvis onboard --module <path> --note …` в фоне,
  как New task. Одно исследование за раз: остальные ждут в очереди (видна позиция, можно убрать);
- папка больше 150 файлов или 15 тыс. строк за один проход описывается плохо — вместо Start предлагаются её части
  (подпапки; без документа отмечены), они встают в очередь по одной, у каждой свой кандидат;
- когда кандидат готов (колокольчик тоже скажет): сколько утверждений подтвердилось, что отброшено и почему,
  превью документа и **Check these first** — обобщения, которые цитата не доказывает: **Accept as a draft** не
  примет, пока все не отмечены. Accept пишет `.jarvis/knowledge/module-<имя>.md` в рабочую копию (как
  `candidates promote`); документ, написанный человеком, страница показывает диффом и заменяет только кнопкой
  **Replace it** — или пишет под другим именем. **Research again with the note** отклоняет кандидата и запускает
  новое исследование с заметкой и списком отброшенного; **Discard** только отклоняет;
- внизу — незакоммиченные файлы `.jarvis/knowledge|standards|skills` и **Commit knowledge**: один коммит
  `knowledge: …` этих файлов с автором из git config репозитория. Push — твой.

Сервер прогоны сам не исполняет, он только запускает CLI. Если карточка этого прогона ждёт в терминале
(`jarvis continue`, `work`), она подхватывает решение и идёт дальше сама; страница так и пишет. Если терминала нет
(прогон начат на странице или терминал оставил карточку через `q`), решение записано, и дальше прогон ведёт
страница: `jarvis resume` в фоне. Вторая попытка решить ту же версию отвергается («decided meanwhile»).

**Resume** появляется у прогона, который никто не двигает, хотя `jarvis resume` двинул бы. Кнопка есть на странице
прогона, а для ждущих решения — ещё и в Waits for you. Это прогон, у которого:
- решение принято (ещё бюджета, Run again, одобрение), но терминала у карточки нет;
- `SUSPENDED` после Ctrl-C;
- `RUNNING` без процесса (прерван или упал);
- пауза на окне квоты (то же, что **Resume now**).

По клику прогон начинает вести страница. Упавший (`FAILED`) кнопкой не продолжается: сначала прочитать, что
упало, потом `jarvis continue`.

Страница обновляется сама: сервер раз в секунду читает хвост `events` (как `jarvis follow`) и шлёт
Server-Sent Events, а страница перерисовывает изменившиеся части. Показывается только то, что видит
терминал: артефакты хранятся после редакции секретов, переменных окружения и сырых ответов модели на
странице нет; всё, что написали агенты, экранируется.

Сервер слушает только `127.0.0.1` (порт 4317, занят — любой свободный; занятый явный `--port N` — ошибка;
`--port 0` — сразу любой). Адрес
содержит случайный токен сессии (`http://127.0.0.1:4317/?t=…`): без него — 403; при первом заходе токен
переходит в cookie и уходит из адресной строки; запросы с чужим `Host` отвергаются. Браузер открывается
сам, если команда запущена в терминале (`--no-open` — только напечатать адрес; `--open` — открыть и без
терминала); открывает `$BROWSER`, иначе `open` / `xdg-open` (Windows — `start`). Ctrl-C останавливает сервер; прогоны он
не трогает: не исполняет workflow и не держит аренду.


### `jarvis shell [run] [--print]`

Шелл (`$SHELL`) в рабочей копии прогона — поправить руками, не копируя путь; `JARVIS_RUN` — короткий id
прогона (для настроек эта переменная не читается). `jarvis c` в этом шелле закрывает его и продолжает
прогон; после `exit` — что изменено и, если прогон ждёт, подсказка `jarvis continue`. Без id — последний
незавершённый прогон этого репозитория. `--print` (и без терминала) — только путь:
`cd "$(jarvis shell --print)"`. Рабочие копии лежат в `~/.jarvis/worktrees/<репозиторий>/<run>-<задача>`.

### `jarvis follow [run]`

Следить за прогоном, который идёт в другом терминале или у демона: его ход с начала (строки шагов), затем
вживую, пока он не остановится ради человека, не закончится или не упадёт, — потом итог. Ctrl-C только
отключается, прогон идёт дальше. Без id — прогон этого репозитория, который идёт сейчас. (`jarvis attach` —
мини-чат уточнений, см. ниже.)

### `jarvis show <run> [artifact] [--raw] [--out <file>]`

Что создал run. Без артефакта — список: `тип/имя@версия`, шаг, «awaiting approval»/«approved»,
«⚠ incomplete», если агент упёрся в лимит. С артефактом (тип, имя или однозначная часть `тип/имя`) —
содержимое для чтения: документ агента (spec, requirements, research — JSON по схеме) показывается как
markdown — заголовок, summary, разделы (требования с критериями приёмки вложенными пунктами), источники в
конце; `--raw` — JSON как хранится. Затем подсказки, как утвердить или вернуть на доработку; `--out`
пишет артефакт в файл как есть. `--json` — метаданные и содержимое.

Список заканчивается тем, что redactor замаскировал в выводе инструментов, по шагам: сколько и каких типов, а
для догадок по энтропии — силуэт значения без самого значения. Это первые три символа, длина, классы символов
и текст перед значением, где длинные последовательности тоже скрыты. По силуэту видно, когда маскировка
ложная: имя из кода или путь. Известные секреты и совпадения шаблонов (токены, ключи) не описываются никак.

```
masked in what agents read (a code name here is a false positive)
  research  3 (high-entropy ×2, bearer ×1)
    const handler = [REDACTED:high-entropy:0a1b2c3d]  isC… 34 chars, mixed case
```

### `jarvis cancel <run>`

Немедленно, если run не исполняется; иначе — после текущего вызова модели или инструмента.

### `jarvis daemon [--interval <s>] [--once]`

Возобновляет припаркованные run без живой аренды (ADR-0002 §5): `WAITING_BUDGET` — после `resumeAfter`,
`WAITING_HUMAN` — когда решение уже записано (одобрение, ответ на уточнение). Упавшие и прерванные не трогает.
`--interval` — секунды между тиками (30); `--once` — один тик.

### `jarvis context [run]`

Контекст агента сейчас: эффективное окно, размер базы (L0–L4), история L5, текущее давление и уровень,
счётчики обрезаний и сжатий. Без аргумента — последний активный run (если таких нет — последний вообще).
Читает только checkpoint, ничего не меняет; без транскрипта в checkpoint (шаг ещё не делал вызовов
инструментов или run между шагами) сообщает об этом.

### `jarvis compact <run> [--aggressive] [--dry-run]`

Обрезает старые результаты инструментов и сворачивает старую историю в handoff, не дожидаясь порога
(ADR-0013). Работает с нетерминальным run, который сейчас не исполняется (например, `WAITING_BUDGET`,
`WAITING_HUMAN`): на 5 минут берёт аренду и сохраняет новый checkpoint, с которого `resume` продолжит. Отказывается для
завершённого run, run без транскрипта и run с чужой арендой. `--dry-run` — только план, без модели и
записи; `--aggressive` оставляет меньше хвоста.

### `jarvis reset-context <run> [--dry-run]`

Заменяет всю историю структурированным handoff (свежее окно); оригинал сохраняется блобом и
перечислен в строке `Originals:`.

Сводку handoff пишет роль `compaction` (или модель агента), до 8000 токенов ответа. Если сводка пришла пустой или
обрезанной, в handoff идут прежний handoff, запись вызовов с тем, где лежит результат, и источники задачи, как их
прочитали (`fallback` в событии `context.compacted`).

## Результат

### `jarvis diff <run>`

Diff worktree run относительно базового коммита.

### `jarvis apply <run> [--message <text>]`

Squash ветки run на текущую ветку основного репозитория одним коммитом; `// REVIEW:` маркеры удаляются
(если `human.review.removeMarkersAfterApproval`).

### `jarvis gc [--days <n>] [--prune-branches]`

Удаляет worktree прогонов `COMPLETED` и `CANCELLED` старше `workspace.retentionDays` (или `--days`); рабочие
копии упавших (`FAILED`) не трогает. С `--prune-branches`
— и ветки `jarvis/*`; чистит устаревшие файлы фактов в кэше графа.

## Участие человека

### `jarvis approve <run> [--type <t>] [--reject | --request-changes] [--comment <text>] [--resume] [--commit]`

Решение по артефакту, который ждёт run (тип выводится из `waitingFor`, `--type` переопределяет).
Утверждение привязано к точной версии и хешу содержимого. `--request-changes` отправляет по
объявленному обратному ребру; `--reject` — run в `FAILED`. `--resume` сразу продолжает. `--commit`
пишет `.jarvis/approvals/<task>/<type>.json` и коммитит — для CI с `humanGate: skip-if-approved`. Версия
решается один раз: повторное решение по ней — ошибка с тем, кто и как уже решил. Карточка, которая ждёт этот
прогон в другом терминале, подхватывает решение сама.

### `jarvis threads [--all]`

Открытые треды (clarification, review, approval, conflict) всех run с тем, чего они ждут.

### `jarvis answer <threadOrRun> [text] [--accept] [--rule <text>] [--reject] [--resume]`

Асинхронный ответ в тред уточнения: текст — реплика человека, после которой агент-кларификатор задаёт
следующий вопрос или предлагает правило; `--accept` принимает предложение, `--rule` — принимает со своей
формулировкой, `--reject` закрывает тред без решения (run продолжает ждать). Решение становится
артефактом `clarification`, обязательным для всех последующих агентов.

### `jarvis attach <run> [--no-resume]`

Тот же тред как живой мини-чат в терминале: печатайте ответ, `a` — принять, `e <rule>` — принять со своей
формулировкой, `r` — отклонить, `q` — выйти. После решения run возобновляется (если не `--no-resume`).

### `jarvis review submit [run] [--resume]`

Собирает `// REVIEW: …` маркеры из workspace run (run выводится из текущего worktree, если не указан),
записывает обратно идентификаторы `REVIEW(R-n):`, создаёт артефакт `review-package` и отправляет гейт
`approve-impl` по ребру `review_submitted` к агенту `review-analysis`.

### `jarvis review status [run]`

Каждое замечание с состоянием жизненного цикла: open → acknowledged → applied → ready_for_review →
resolved, классом (CODE, SPEC_CORRECTION, …) и историей.

## Знание проекта

### `jarvis standards list`

Стандарты проекта и пользователя: scope, severity, вид проверки.

### `jarvis standards check [--base <ref>]`

Детерминированные проверки (pattern / tool) по файлам, изменённым относительно `--base`.

### `jarvis skills list [--agent <id>]`

Встроенные, проектные и пользовательские навыки; какие были бы выбраны для типовой задачи данного
агента.

### `jarvis candidates list [--all] | show <имя> | promote <имя> [--id <id>] [--replace] | reject <имя> [--comment]`

Кандидаты в стандарты/знание, предложенные агентами ревью и онбординга. У кандидата есть имя — от
того, о чём он: карта модуля `packages/shared-lib/src/billing` называется
`shared-lib/billing` (без `src` и `packages/`/`apps/`/`services/`/`libs/`), прочие — слаг
заголовка. Если о том же есть несколько кандидатов, простое имя у самого нового, у старших — с
суффиксом прогона: `…/billing@a1b2c3d4`. Везде, где нужен `<имя>`, годится любая однозначная часть
имени (`billing`, `plugins`) или id артефакта; при неоднозначности команда перечисляет совпадения,
а открытый кандидат предпочитается решённому.

- `list` — по каждому: тип, заголовок, прогон и давность; сколько утверждений подтверждено, сколько
  отброшено и сколько обобщений проверить; код, к которому относится, и файлы, на которые чаще всего
  ссылаются цитаты (куда смотреть); первые три обобщения со знаком `?`. В конце — подсказки команд.
- `show` — документ ровно в том виде, в каком его запишет `promote`, путь файла и полный список
  обобщений, которые надо проверить по коду перед принятием.
- `promote` пишет файл в `.jarvis/standards/`, `.jarvis/knowledge/` или `.jarvis/skills/<id>/IMPROVEMENT.md`
  (карта модуля — `module-<имя>.md`, где `/` в имени заменены на `-`: `module-shared-lib-billing.md`; `--id`
  задаёт другое) и записывает решение; файл ваш — правьте и коммитьте
  обычным ревью. Сгенерированный файл (с маркером onboard) заменяется; написанный человеком — только с
  `--replace`, иначе отказ с подсказкой. `reject` — только решение.

### `jarvis knowledge update [--full]`

Инкрементальное обновление графа проекта: факты по файлам из кэша по хешу содержимого, рёбра — на
снимок дерева; `--full` игнорирует кэш. Нужен адаптер стека уровня FULL (сейчас TypeScript).

### `jarvis knowledge status [--verify]`

Последний снимок графа (узлы, рёбра, дерево); `--verify` пересчитывает без кэша и сравнивает — проверка
детерминизма (ADR-0008).

### `jarvis knowledge index`

Индексирует секции знания, стандарты и навыки (FTS5; векторы — если задано
`knowledge.retrieval.embeddings`). Агенты индексируют автоматически при подготовке контекста.

### `jarvis knowledge search <query> [--limit n]`

Поиск так, как его видят агенты: расширение запроса по глоссарию, лексический и (при наличии) семантический
индексы, слияние RRF, путь извлечения у каждого результата.

### `jarvis ask <вопрос…> [--no-llm] [--general] [--limit n]`

База знаний проекта как справочник. Работает в два слоя:

1. **Без модели.** Термины и аббревиатуры вопроса, найденные в `glossary.md` (по целому слову или
   фразе, термин или синоним), выводятся прямо из глоссария: определение, синонимы, символы кода,
   источники. Рядом — ближайшие источники из индекса (документы знания, стандарты, навыки) с выдержками.
   Модель не вызывается, если источников не нашлось (и нет `--general`) или задан `--no-llm`.
2. **Ответ.** Если источники нашлись, агент `knowledge-answerer` (workflow `ask`, только `knowledge.read` и
   `knowledge.search`, кода он не видит) отвечает структурно и **только по базе**. Каждый источник он
   подтверждает дословной выдержкой; цитаты сверяются с текстом источника, и ответ без подтверждённой
   цитаты не показывается: команда скажет «в базе подтверждённого ответа нет» и покажет ближайшие источники.
   Непокрытая часть вопроса выводится отдельным списком. Если в базе вообще ничего нет, модель не вызывается.

`--no-llm` — только глоссарий и источники. `--general` разрешает отдельную, явно помеченную заметку «не из базы
знаний» из собственных знаний модели; в `answer` она никогда не попадает. Если модель недоступна, команда
показывает глоссарий и источники и пишет об этом. `--json` — полный результат (`terms`, `sources`, `answer`,
`citations`, `rejectedCitations`, `gaps`, `general`, `runId`).

Колонка «определение» в `glossary.md` необязательна и шестая:
`| термин | синонимы | символы/модули | источники | обновлено | определение |`.
Справочник знает ровно то, что записано в `.jarvis/` (документы, стандарты, навыки, глоссарий): общих знаний о React
в нём нет, пока их не добавили. Заполнять базу помогают `jarvis onboard`, `candidates promote` и ручные документы.

### `jarvis explain <file>[:<line>] | <commit> | <run>`

Зачем существует изменение. Строка проходит `git blame` до коммита, трейлер `Jarvis-Run` коммита (его
пишет `jarvis apply`, в том числе при `--message`) указывает на run, а run раскрывается в задачу, шаги,
артефакты с источниками и утверждениями (кто и когда), уточнения и review-треды, счёт вызовов
инструментов и модели. Для файла/строки у артефактов показаны строки, где он упоминается. Файл без номера
строки — все run, менявшие его. Коммит без трейлера объясняется как «не от Jarvis»; run, которого нет на
этой машине, — подсказкой `jarvis import`. `--json` — тот же разбор структурой. Только чтение.

## Git hooks

### `jarvis hooks install [--force] | uninstall | status`

`install` пишет в `.git/hooks/pre-push` (с учётом `core.hooksPath` и linked worktrees) тонкий скрипт,
который передаёт ссылки, отправляемые `git push`, в `jarvis prepush --hook`. Повторный `install`
обновляет свой хук; чужой не трогается без `--force` (он сохраняется как `pre-push.pre-jarvis` и
возвращается при `uninstall`). Если `jarvis` не найден в PATH, хук использует CLI этой установки, а
при его отсутствии не блокирует push. `status` — установлен ли хук и действующая политика `hooks.prePush`.

### `jarvis prepush [--base <ref>] [--head <ref>] [--semantic | --no-semantic] [--hook]`

Проверки перед push по диапазону коммитов (по умолчанию: текущая ветка от upstream/`origin/main`; в
режиме `--hook` — отправляемые ветки от tip удалённой):

1. стандарты — детерминированные проверки по изменённым файлам;
2. `hooks.prePush.checks` — команды из `tools.local` (typecheck, lint, tests);
3. влияние по графу проекта — зависимые файлы и покрывающие тесты, которых изменение не коснулось;
4. ревью агентом `review` (встроенный workflow `review-diff`, только чтение) — при
   `semanticReview: always`, применимых semantic/hybrid-стандартах или находках п. 3; не запускается,
   если п. 1–2 уже блокируют.

Выход 1 в режиме `block`, если есть required-нарушение, упавшая проверка или замечание ревью не ниже
`blockOn`; в `advisory` только отчёт. Недоступное ревью (нет модели роли `review`, квота, ошибка) не
блокирует. `--semantic`/`--no-semantic` перекрывают конфигурацию на один запуск. Обход:
`git push --no-verify` или `JARVIS_SKIP_HOOKS=1`. `--json` печатает отчёт по каждому диапазону.

## CI и перенос

### `jarvis ci <task> [--workflow <name>] [--summary <file>] [--bundle <file>]`

`work` под профилем `ci` (или `--profile <name>`): неинтерактивно, checkout только для чтения. Markdown-сводка —
в `--summary`, иначе `$GITHUB_STEP_SUMMARY` или `JARVIS_CI_SUMMARY`. На гейте (выход 10) или паузе квоты (11) —
`approval-request.json` и `summary.md` в `~/.jarvis/runs/<run>/`. `--bundle` экспортирует run всегда.
`humanGate: fail` → выход 12.

### `jarvis export <run> [--out <file>]` / `jarvis import <bundle>`

Один gzipped JSON: строки run, артефакты и блобы, эффекты, утверждения, треды, патч workspace.
`import` восстанавливает worktree от базового коммита с патчем и отказывается от дубликатов.

## Evals

### `jarvis evals run --suite <s> [--mode live|record|replay] [--variant k=v …] [--out <file>]`

Прогон кейсов `evals/<suite>/<case>/case.yaml` на fixture-репозитории с кассетой; гейты утверждаются
автоматически; метрики: тесты, file recall, покрытие acceptance, обязательные источники, циклы, токены,
`successes per 10k output tokens`. Результат в `evals/results/`.

### `jarvis evals run-to-case <run> --suite <s> [--id <id>] [--no-fixture]`

Из завершённого run — кейс: fixture на базовом коммите (`git archive`), gold из того, что человек принял
(spec/impact/research предпочтённых версий), тестовая команда из `tools.local`.

### `jarvis evals baseline <suite> [--from <file>]` / `jarvis evals diff <suite> [--tolerance r] [--from <file>]`

Зафиксировать последний результат как базовый; сравнить последний с базовым, ненулевой код при регрессии
больше допуска (по умолчанию 5 %).
